# 運用方針

## 目的

本サイトは、自動収集ではなく人による確認を基本とします。この文書は、公開中の公式情報への案内を安全かつ継続可能な範囲で維持するための確認頻度、状態管理、公開、プライバシー、情報量の原則を定めます。

第一版は2026年8月4日に公開済みです。GitHub Pagesで現在公開中なのは日本語・英語、2分野、3カード、14案内先です。リポジトリ内のproduction成果物はBL-006-Bを反映した3分野、4カード、16案内先であり、公開反映にはPRのマージ後に手動デプロイが必要です。正式URLは <https://madoguchi.kokoromimamori.na0aaooq.com/> で、GitHub Pages、カスタムドメイン、HTTPSを使用します。

公開後の個別改善、継続運用、中長期構想は[公開後バックログ](POST_LAUNCH_BACKLOG.md)で管理します。

## 定期確認

### 確認頻度

| 対象         | 原則  | 補足                              |
| ------------ | ----- | --------------------------------- |
| 常設主リンク | 週1回 | 必要に応じて臨時確認する          |
| 補助リンク   | 月1回 | 公式SNSや補助的な案内先などを含む |

現在のproductionに期間限定リンクは実装していません。将来実装する場合の頻度と確認手順は、対象・表示期間・運用負担を設計したうえで決定します。

実際の確認日や次回確認日は、確認記録を根拠に管理します。この文書では推測して追加しません。

### 確認内容

- URLが開くか
- 公式サイトから外れていないか
- ページの役割が変わっていないか
- 案内目的に合っているか
- 古い災害情報だけのページになっていないか
- 公式性の確認根拠が維持されているか
- 日本語・英語の案内文が現在のリンク先と整合するか

### 注意事項

- 自動的に公式性を判定しない
- 現在状況を転載しない
- 確認できない状態で推測更新しない
- URL変更時は公式性と案内目的を再確認する
- 定期確認日そのものを、リンク先内容の正確性・最新性・完全性の保証としない

定期確認は一度完了して終了する開発タスクではなく、公開中に繰り返す`ongoing`運用です。

## 確認日の意味

### 案内先確認日

URLが開くこと、公式サイトから外れていないこと、案内目的に合うことなどを確認した日です。リンク先のすべての内容の正確性や、現在の災害・運行・供給状況を保証する日ではありません。

### 公式情報確認日

団体公式サイトからのリンク、公式SNS一覧、公式のお知らせなど、掲載基準に基づく公式性の根拠を確認した日です。認証バッジやフォロワー数だけを確認した日ではありません。

現在の利用者向けproduction画面には、案内先確認日と公式情報確認日を表示します。確認根拠の説明と根拠URLは管理データ・内部検証に使用し、利用者向け画面には表示しません。

## URL変更・エラー時の扱い

1. 404、リダイレクト、アクセス不能、役割変更を人が確認する
2. 団体の公式トップページや公式サイト内の案内から移転先を調べる
3. 公式性と案内目的を再確認する
4. 根拠、対象URL、案内先確認日、公式情報確認日を必要に応じて更新する
5. 確認できるまで保留または非表示にする
6. 公開対象を変更する場合は、管理データ、日英、生成成果物、検証、公開手順を整合させる

非公式の転載ページや検索結果だけを代替リンクにしません。リンク切れを理由に、現在状況を本サイトへ転載しません。

## 災害別・期間限定案内

災害別・期間限定の公式案内は現在のproductionでは未実装です。

`disasters`、`events`、`disaster-source-links`、`event-source-links`にはデータファイルとSchemaが存在しますが、2026年8月4日時点の本番用管理データに項目はありません。`site_guidance_status`、`publication_status`、表示期間などの構造を利用して運用中とは扱いません。

将来実装を検討する場合は、次を維持します。

- 人が有効性、開始日、終了日を確認する
- 速報値や現在状況を転載しない
- 自動表示・自動終了を前提としない
- 非表示や`archived`が、災害終了、安全、復旧を意味するものとしない
- 深い災害別URLを常設主リンクとして恒久的に残さない

実施可否と設計は[公開後バックログのBL-011](POST_LAUNCH_BACKLOG.md#bl-011-災害別期間限定の公式案内)で管理します。

## 確認・更新履歴

`check-history`と`update-history`にはデータファイルとSchemaがありますが、2026年8月4日時点の本番用管理データは空です。内部確認履歴の記録運用と、公開更新履歴の利用者向けページは現在未実装です。

将来履歴を利用する場合も、内部確認履歴と公開更新履歴を分離し、次を利用者向けに公開しません。

- 作業中の内部メモ
- 公式性を確認していないURL
- 公開前の候補情報
- 個人情報やセンシティブ情報
- セキュリティ上公開すべきでない情報
- 問い合わせに含まれる個人情報

履歴表示は確認作業の透明性を目的とし、リンク先内容の正確性や現在状況を保証する証明としません。利用者向け表示の実施可否は[公開後バックログのBL-014](POST_LAUNCH_BACKLOG.md#bl-014-確認更新履歴の利用者向け表示)で管理します。

## 現在の情報量と将来の上限目安

### 現在のproduction

| 対象       | 現在の情報量 |
| ---------- | ------------ |
| 公開分野   | 3分野        |
| 案内カード | 4カード      |
| 案内先     | 16件         |

### 将来拡張時の運用目安

次は将来拡張時に確認する上限の目安であり、現在実装済みの情報量ではありません。

| 対象                         | 上限・目安 |
| ---------------------------- | ---------- |
| 公開画面上のまとまり         | 約17       |
| 管理する情報源               | 30件以内   |
| 常設・補助リンク             | 45件以内   |
| 同時に表示する期間限定リンク | 8件以内    |
| 一つのカードの主な案内先     | 原則1〜3件 |

上限は情報不足を正当化するためではなく、確認漏れ、選択肢過多、更新負担の増大を防ぐための管理基準です。実運用で変更する場合は、理由と確認体制への影響を記録します。

## 新規追加時の判断

新しい案内カード、団体、案内先を追加する前に、次を確認します。

- 既存情報で代替できないか
- 現在の対象地域と目的に直接関係するか
- 公式性の根拠を人が確認・記録できるか
- 日本語・英語の案内を維持できるか
- 定期確認の負担が許容範囲か
- 情報量を増やしても利用者が迷いにくいか
- 支援・復旧分野の特別ルールに合うか
- 情報量上限の範囲内か

網羅性より、丁寧に維持できる範囲を優先します。未掲載は団体の評価ではなく、掲載基準と継続確認可能な範囲による判断です。案内カード等の追加と掲載対象地域の拡大は分離し、それぞれ[BL-008](POST_LAUNCH_BACKLOG.md#bl-008-案内カード団体案内先の段階的追加)と[BL-009](POST_LAUNCH_BACKLOG.md#bl-009-掲載対象地域の拡大)で管理します。

## 重複管理の防止

同じ団体、URL、公式アカウント、相談先は一つの情報として管理し、複数のページ・分野から共通参照します。管理単位、coreとlocale、参照関係は[データモデル](DATA_MODEL.md)と実装済みのSchemaに従います。

管理データ、Schema、公開成果物を直接または推測で変更しません。正本を変更する場合は、人による確認、日英整合、検証、生成、差分確認、公開ゲートを維持します。

## スプレッドシート入力補助

確認状態、公開状態、確認日などのGoogleスプレッドシート入力を補助するGAS等は未実装です。使用技術、対象範囲、dry-run、明示確認、誤操作防止を設計し、人による公式性判断と公開ゲートを弱めない範囲で将来実施する`planned`項目です。

入力補助は、外部サイトの自動巡回、`confirmed`・`published`への自動変更、GitHubへの自動反映、PR作成、GitHub Pagesへのデプロイを行いません。詳細は[公開後バックログのBL-010](POST_LAUNCH_BACKLOG.md#bl-010-googleスプレッドシート入力を補助するgas等)を参照してください。

## 公開と復旧

productionはGitHub Pagesで公開し、カスタムドメインとHTTPSを使用します。`.github/workflows/deploy-pages.yml`は`workflow_dispatch`だけで実行する手動workflowです。`main`へのpushやPRマージで自動デプロイしません。

公開対象は`dist/site/production`だけです。管理用`data/`、Schema、テスト、文書、実在TSVをPages artifactへ含めません。生成・手動デプロイ・公開後確認・復旧は[GitHub Pagesへのproductionサイト手動デプロイと公開後運用](GITHUB_PAGES_DEPLOYMENT.md)に従います。

## プライバシーとアクセス解析

productionでは、サイトの利用継続、掲載情報・画面構成・公式情報への案内機能の改善、災害時等との利用傾向比較、メンテナンス計画の判断に必要な最小限の範囲でGoogle Analytics 4を使用します。アクセス数だけで利用者の意図や原因を断定せず、アクセスが少ないページを公的情報として重要でないとは判断しません。

Googleタグマネージャーを使用せず、`site/production.json`で一元管理する測定IDから、Google標準の静的`gtag.js`タグをproduction全HTMLと404へ直接出力します。previewへタグ、測定ID、Google Analyticsの説明を出力しません。production成果物をローカルで開いた少量の計測は許容しますが、生成・テスト・検証は外部ネットワークへ接続しません。

ページビューとGoogle Analytics 4の拡張計測による外部サイトへの離脱クリックだけを利用します。独自イベント、独自の外部リンククリック計測、404専用イベント、Googleタグマネージャー、Googleシグナル、User-ID、広告配信・広告パーソナライズ、クロスドメイン計測、内部トラフィック除外、Cookie同意バナーは初期導入に含めません。レポートのタイムゾーンはJST、ユーザー単位・イベント単位のデータ保持期間は14か月です。

Google Analytics 4はCookieを使用します。一方、運営者は独自のアクセス解析システム、広告目的のトラッキング、localStorageを使用しません。文字サイズ設定のため、sessionStorageへ`standard`または`large`だけを保存します。sessionStorageを利用できない場合も標準サイズで主要情報を利用できます。ホスティングにはGitHub Pagesを使用し、配信に必要な技術情報がホスティング提供者側で処理される可能性があります。GoogleによるAnalytics提供に必要な処理と、運営者による第三者提供を区別して日英のプライバシーポリシーへ記載します。

法令、対象地域、事業形態、Googleの規約や機能に変更がある場合は、同意の要否を含めて改めて確認します。公開後は、運営者がGA4でpage_view、外部リンクclick、`link_url`・`link_domain`、404のpage_view、`_ga`等のCookie、無効にした拡張イベント、タグの二重送信を手動確認します。
