# データ検証・公開生成方針

## 文書の位置付け

この文書は、管理データを公開成果物へ変換する前後の検証責務、結果区分、停止条件、人による最終確認を定めます。第一版は未実装です。

このPRでは、検証プログラム、JSON Schema、実データ、公開生成処理を実装しません。具体的な製品・ライブラリ・コマンドは後続工程で決定します。

## 基本原則

- 第一版のJSON Schema仕様はDraft 2020-12に固定する
- JSON Schemaによる単一ファイル内の構造検証と、独自処理によるファイル間の意味検証を分ける
- 検証結果をError、Warning、Infoの3段階で扱う
- Errorが一つでも存在する場合は公開成果物の生成を停止する
- 公開対象だけを抽出し、内部専用項目を除外する
- 生成後にも内部項目の混入を再検証する
- 自動検証だけで公開可能と断定せず、人による最終確認を必須とする

## JSON Schemaの基準

第一版ではJSON Schema Draft 2020-12を使用します。これは常に最新のDraftへ追従するという意味ではなく、第一版の実装基準を固定する判断です。

想定する構成は次のとおりです。

- `schemas/manifest.json`
- `schemas/common/`
  - `definitions.schema.json`
  - `file-envelope.schema.json`
  - `locale-record.schema.json`
  - `relation-record.schema.json`
- `schemas/core/`
  - 各`data/core/` JSONに対応するスキーマ
- `schemas/locales/`
  - 各`data/locales/ja/`・`data/locales/en/` JSONに対応するスキーマ

`manifest.json`は、検証対象ファイル、適用するスキーマ、言語、公開生成時の扱いを一元的に関連付けます。共通スキーマはID、日付、URL、ファイル外枠、locale共通項目、関連データ共通項目などを再利用可能にします。

各スキーマは`additionalProperties: false`を基本とし、想定外の項目を見逃さない設計とします。

## JSON Schema検証の責務

JSON Schemaでは、主として次を確認します。

- JSON構文
- 型
- 必須項目
- 列挙値
- 日付形式
- URL形式
- ID形式
- 空文字列
- 配列内の重複
- 最小件数
- 条件付き必須項目
- 想定外の項目

JSON Schemaは、一つのレコードまたはファイル内部で宣言的に確認できる制約を担当します。ファイルをまたぐ参照や運用上の意味は独自の意味検証へ分離します。

## 意味検証の責務

独自の意味検証では、主として次を確認します。

- ファイル間のID参照がすべて存在する
- 管理対象ごとにIDが重複していない
- URLの正規化後に重複がない
- 地域などの親子関係に自己参照・循環がない
- 公開中の案内先に必要な確認日がある
- 公開中の案内先に有効な公式情報の確認根拠がある
- 公開対象言語の日英localeが存在し、公開可能な状態である
- 日本語の`content_revision`と英語の`based_on_ja_revision`が一致する
- `official-ja-fallback`が日本語正式名称と一致する
- `official-en`に公式名称の根拠が関連付いている
- 同じ対象と案内先の関連データが重複していない
- 同一表示範囲で`display_order`が重複していない
- 表示開始日と終了日に矛盾がない
- トップ案内が最大5件を超えない
- アーカイブ済みデータを公開中データが参照していない
- 内部専用項目が公開成果物へ混入していない
- 日本語だけのリンク先を英語版へ表示する場合、リンク先言語の案内がある
- 出来事が必ず一つの災害へ属している
- 出来事がトップ上部へ直接表示されていない
- 未対応言語が指定されていない

## 検証結果の区分

### Error

公開成果物の生成を停止します。例は次のとおりです。

- JSON構文エラー
- JSON Schema違反
- ID重複
- 存在しない参照
- URL重複
- 公開必須項目の不足
- 日英locale不足
- 改訂番号不一致
- 公式情報の確認根拠不足
- 掲載期間の矛盾
- トップ案内の上限超過
- 内部項目の公開混入
- 公式英語名称の根拠不足
- 未対応言語の指定

Errorは、一部レコードだけを黙って除外して処理を続ける理由にしません。原因を特定できるファイル、ID、検証規則を報告して停止します。

### Warning

公開成果物の生成は可能ですが、人による確認を必要とします。例は次のとおりです。

- 案内先確認が運用周期を超過している
- 公式情報確認の再確認時期を超過している
- `other`分類を使用している
- 任意説明文が未登録である
- 期間限定案内の終了確認が不足している
- ボタン文言や説明文が長い
- 類似する案内先が複数存在する

安全性への影響が大きい期限超過は、設定された条件によりErrorへ昇格できる設計とします。例えば、トップ表示中の期間限定案内が許容期限を超過している場合です。具体的な運用周期と昇格条件は後続工程で定めます。

### Info

対応を必須としない処理情報です。例は次のとおりです。

- 下書きデータを公開対象から除外した
- 言語別・種別別の公開件数
- 英語版から日本語ページへ案内するレコードがある
- 内部確認だけを記録した
- アーカイブデータを管理用に保持した
- 公開成果物の生成が完了した

## 終了コード

検証・公開生成コマンドの終了コード候補は次のとおりです。

| 終了コード | 意味 |
| --- | --- |
| `0` | Errorなし |
| `1` | データ検証Errorあり |
| `2` | 設定不足、読込失敗、検証処理自体の異常 |

Warningの存在だけでは終了コードを`1`にしません。ただし、人による確認が必要であることを明確に報告します。具体的なCLI仕様は後続工程で定めます。

## 公開生成手順

将来の公開生成処理は、次の順序を基本とします。

1. manifestに基づいてJSONファイルを読み込む
2. JSON構文を検証する
3. JSON Schemaを検証する
4. ID索引を作成する
5. ファイル間の参照を検証する
6. URL、日付、公開状態を検証する
7. 日英localeの存在、状態、改訂番号を検証する
8. 公式情報の確認根拠を検証する
9. 災害、出来事、3種類の関連データを検証する
10. Errorがあれば停止する
11. WarningとInfoを報告する
12. `published`データだけを抽出する
13. 内部専用項目を除外する
14. 日本語版・英語版の公開成果物を生成する
15. 生成物へ内部項目が混入していないか再検証する
16. 人による最終確認項目を表示する

各段階は、検証失敗の原因がファイルとIDまで追跡できるようにします。

## 公開対象の抽出

`publication_status`が`published`であり、必要なlocaleの`locale_status`が`published`で、表示期間と参照先の公開条件を満たすデータだけを抽出します。

次は公開成果物へ含めません。

- `internal_note`
- `checked_by`
- 内部確認履歴の`summary`
- 非公開URL
- 調査途中の記録
- `draft`
- `under-review`
- `hidden`
- `archived`
- `needs-update`
- その他の公開対象外データ

`data/core/check-history.json`自体を公開成果物へ含めません。公開更新履歴は、専用の`update-history.json`と公開可能な日英文面から生成します。

## 内部項目の除外と再検証

内部項目の除外を、ブラウザ側JavaScriptや表示上の非表示だけに依存しません。公開生成時にデータから物理的に除外し、生成後のファイル一覧と内容を再検証します。

再検証では、少なくとも次を確認します。

- 管理用ファイルが公開ディレクトリへコピーされていない
- 禁止した内部キーが生成物に存在しない
- 下書き・確認中・非表示・アーカイブのレコードが存在しない
- 非公開URLや内部確認履歴が存在しない
- 日本語版・英語版ごとに必要な公開文面だけが含まれる

## 人による最終確認

機械検証だけで公開可能と断定してはいけません。公開前に人が次を確認します。

- 本当に意図した公式ページか
- 団体や案内先の説明が誤解を招かないか
- 英語文が日本語の意味と一致するか
- 独自訳を公式英語名称として扱っていないか
- 現在の被害、停電、断水、運休、診療状況などを転載していないか
- 個人情報やセンシティブ情報を含んでいないか
- 「最新」「安全」「正しい」などを保証していないか
- 110番・119番が誤操作しやすい発信リンクになっていないか
- 日本語だけの外部ページであることが英語版に明示されているか
- 表示順が評価や推奨順位に見えないか
- モバイルやキーボード操作で利用できるか
- JavaScriptや画像がなくても主要機能を利用できるか

Warningがある場合は、対象ごとの確認結果を残してから公開判断を行います。

## この文書で決定しないこと

次は後続工程で検討します。

- 検証プログラムの実装言語
- JSON Schemaバリデータ
- テストランナー
- Linter、Formatter
- CI/CDへの組み込み方
- 具体的なコマンド名と出力形式
- 確認期限とWarningからErrorへの昇格条件
- 公開成果物の具体的なディレクトリとURL
- 自動デプロイ方式
