## 1. 目的

- [開発作業標準フロー](DEVELOPMENT_STANDARD_FLOW.md)を管理し、開発判断に必要な情報確認を標準化する。
- 「まどぐちみまもり」が、利用者様を公的機関・関係団体の公式情報・公式窓口へ安全かつ迅速に案内する目的を達成できるようにする。
- 確認済み情報と未確認情報を分け、判断根拠を後から確認可能にすることで、判断品質を維持する。

## 2. 基本原則

- 確認できない情報を確認済みとして扱わない。
- 確認済み情報と推測を分離する。
- 開発作業標準フローは目的達成のために利用する。

## 3. 管理ルール適用時の優先順位

管理ルールを適用する際は、以下の優先順位とする。

1. 利用者様が国・地方公共団体その他の公的機関・関係団体の公式情報・公式窓口へ安全かつ迅速に到達できること
2. 確認可能な情報に基づき判断すること
3. 開発目的を達成すること
4. 開発作業標準フローを適切に適用すること

## 4. 適用範囲

### Phase 0〜Phase 6の標準フローを適用する変更

- 新機能開発
- 地域追加
- データ追加
- データ構造変更
- 公開仕様変更
- 設計変更
- CI/CD変更
- 開発プロセス・運用ルール変更
- その他既存仕様へ影響する変更

### Phase 0〜Phase 6の標準フローをそのまま適用しない変更

- 軽微な誤字・表現・表示等の修正
- 本番障害・セキュリティ問題等への緊急対応

これらは本管理ルール自体の対象外ではない。具体的な適用方法は「5. 変更種別と適用判断」に従う。

## 5. 変更種別と適用判断

### A. 標準フロー適用

対象：

- 新機能追加
- 地域追加
- データ追加
- データ構造変更
- 公開仕様変更
- 設計変更
- アーキテクチャ変更
- 開発プロセス・運用ルール変更

対応：

Phase 0〜Phase 6を実施する。

### B. 軽微変更（簡略適用）

対象：

- 誤字修正
- 表現修正
- 表示崩れ修正
- ドキュメントのみ修正

対応：

影響範囲に応じて必要なPhase・確認のみ実施する。

ただし、変更内容と簡略適用と判断した理由を記録する。

ドキュメントのみの変更であっても、要件、設計、公開仕様、運用ルール、開発プロセス、アーキテクチャ等の変更を伴う場合は、ファイル種別だけを理由にBへ分類しない。変更内容と影響範囲に基づいてAを検討する。

### C. 緊急対応

対象：

- 本番障害
- セキュリティ対応
- その他、利用者の安全確保またはサービス復旧を優先する必要がある重大な問題

対応：

- 安全確保・復旧を通常フローより優先する。
- Phase 0の事前完了を対応開始条件としない。
- 緊急性を理由に不要なScope拡大を行わない。
- 確認可能な範囲で現在状態、影響範囲、安全性、実施内容を確認する。
- 利用者の明示承認ルールは自動解除しない。
- 対応後に事後レビューを行う。

事後レビューでは、最低限、以下を整理する。

- 発生した問題
- 緊急対応と判断した理由
- 正式な変更種別
- 実施した変更
- 確認できた情報
- 確認できなかった情報
- 検証結果
- 未解決事項
- 必要な再発防止・追加対応

作業開始時は変更種別を仮分類し、原則としてPhase 0で正式判断する。ただし、変更種別CではPhase 0での事前正式判断を必須とせず、対応後の事後レビューで正式に整理できる。

## 6. 正本管理

- 開発作業標準フローの管理・適用判断・変更種別・情報確認原則の正本は、`docs/DEVELOPMENT_PROCESS_RULES.md`とする。
- Phase 0〜Phase 6の詳細な開始条件、入力情報、実施手順、成果物、完了条件、終了判定の正本は、`docs/DEVELOPMENT_STANDARD_FLOW.md`とする。
- `README.md` および `docs/README.md` は、正本文書への入口として利用する。
- `AGENTS.md` は、開発エージェントがリポジトリで作業する際の実務ルールとし、正本文書と矛盾しないよう維持する。

## 7. 情報確認時の優先順位

情報を確認する際は、以下の優先順位とする。

1. 現在のリポジトリ状態
2. 最新の正本ドキュメント
3. 最新のコード・設定
4. Pull Request / Issue
5. 引き継ぎプロンプト
6. 過去の会話内容

## 8. 参照不能時の対応

参照対象には、次のような資料を含む。

- GitHubリポジトリ
- README.md
- AGENTS.md
- 設計資料
- 「まどぐちみまもり_掲載情報」Googleスプレッドシート
- 外部参考サイト
- 本番環境

資料名やURLが存在するだけでは参照済みとは扱わない。

作業判断に必要な実内容を確認できた場合のみ、参照済みとして扱う。確認できない場合は、確認できない事項として明示し、推測で補わない。

## 10. 更新管理

本ルールを更新する場合は、次を管理する。

- Version管理
- 更新日

- 変更概要

## 11. 更新責任

本ルールの更新時は、更新内容、更新理由、変更概要およびVersionを明確にし、正本である`docs/DEVELOPMENT_PROCESS_RULES.md`へ反映する。

## 12. 例外対応

本ルールを通常どおり適用できない場合は、例外の内容、理由、確認できない事項および判断への影響を明示する。確認できない情報を推測で補ってはならない。

## 13. レビュー・改善

開発作業で確認された資料の確認漏れ、テスト手順の抜け漏れ、引き継ぎ情報不足、確認済み情報と推測情報の混在を、今後のレビュー・改善へ反映する。更新時は「10. 更新管理」に従って記録する。

## 14. Phase 0開始前の最低限入力情報

Phase 0を開始する前に、最低限、以下の情報を揃える。

通常対応では、以下の8項目をPhase 0開始前の最低限入力情報とする。変更種別Cでは、Phase 0の事前完了を対応開始条件としないため、本節の入力情報を緊急対応開始前にすべて揃えることを必須としない。対応後の事後レビューで、確認可能な情報を整理する。

1. プロジェクト名
2. GitHubリポジトリ
3. ローカルのソース格納ディレクトリ
4. 変更種別（仮）
5. 変更概要
6. 目的
7. 関連資料
8. 開発開始前であること
