# 0018: 管理単位ごとのJSON Schemaを採用する

## 状況

確定したcore・localeの管理単位を本番用データファイルとして配置し、後続の縦切り実装前から配置と構造を検証できる土台が必要です。一方、各itemの構造はまだ実装対象ではなく、複数Schemaで安定して共有できる定義も固まっていません。

## 決定

JSON Schema Draft 2020-12を使用し、管理単位ごとにSchemaを分けます。coreは14 Schema、localeは13 Schema、合計27 Schemaとし、日本語と英語は同じlocale Schemaを利用します。

`site.json`は単一オブジェクトとし、その他は`schema_version`、`data_updated_on`、`items`を持つ配列エンベロープとします。工程3-1で未実装の管理単位は`maxItems: 0`で保護します。core 14、日本語13、英語13の合計40データファイルを先に配置します。

初期段階では複数Schemaから参照する共通Schemaを作らず、外部Schemaへの参照やリモート取得も使用しません。工程3-1では実在する団体、URL、災害情報を追加しません。工程3-2で、明確な架空データによる最小縦切りと必要なitem Schemaを実装します。

## 理由

- 管理単位ごとの変更範囲と責務を追跡しやすい
- 日本語と英語の構造差を作らず、locale Schemaの重複を避けられる
- 初期段階では共通化による間接参照より、各Schemaを単独で理解できることを優先できる
- `maxItems: 0`により、正式なitem Schemaがない状態でデータだけが追加されることを防げる
- 外部通信に依存せず、同じリポジトリ内容をローカルで再現可能に検証できる

重複よりも、各管理単位の独立性と理解しやすさを優先します。実装が進み、複数Schemaの共通部分が安定してから共通化を再検討します。

## 影響

工程3-1ではエンベロープ定義が25 Schemaへ重複します。変更時は管理単位ごとの差異を確認し、`npm run validate:data`とテストで全Schemaを検証します。画面、公開生成、全意味検証、実在情報はこの決定だけでは実装されません。
