# ADR 0022: 公開用navigation成果物を生成してGit管理する

## 状況

管理用`data/`には公開判定、確認根拠、内部メモ、表示順など画面へ不要または公開禁止の情報があります。画面が管理データを直接読み込むと、結合・公開判定・内部項目除外の責務が画面へ漏れ、日英の表示内容とレビュー対象も把握しにくくなります。

## 決定

- 日本語・英語ごとに1つの`navigation.json`へ非正規化する
- 管理用27 Schemaと公開成果物専用Schemaを分離する
- 公開カードから到達可能なsourceとpublisher organizationだけを抽出する
- publishedの5分野はカード0件でも含める
- stable IDを残すが、画面表示、認証、認可に使用しない
- `display_order`は並べ替えだけに使い、成果物へ出力しない
- evidenceは公開可否の内部判定だけに使い、成果物へ出力しない
- `visibility_context`を表示場面の機械向け項目として残す
- previewとproductionを分離し、正式な日英成果物だけをGit管理する
- 成果物を直接編集せず、正本・fixture・生成処理から再生成する
- `--as-of`の日付単位で期間判定し、現在日時を自動採用しない
- 期間・言語判定後にprimaryが消える場合は生成全体を停止する
- draft正本からproductionを生成せず、非公開正本に古いproductionが残ればErrorにする
- allowlist方式で公開オブジェクトを作り、公開Schema、禁止項目、URL安全条件を検証する
- 同じ入力・同じ基準日でバイト一致する決定論的なJSONを生成する
- 災害、出来事、画面、実在情報、AWSは対象外とする

### 採用しなかった案

- `data/`を画面で直接読む案: 管理項目が公開境界を越え、画面へ結合と公開判定の責務が漏れるため採用しない
- draftをpreviewとして自動公開する案: draftの誤公開につながるため、専用published架空fixtureを使う
- `display_order`を公開する案: 並べ替え後の配列で十分で、管理値を公開する必要がない
- evidenceを公開する案: 根拠は内部の公開可否判定に必要だが、navigation画面の契約には不要である
- `dist`全体をGit管理する案: 一時物や一般ビルド成果物まで混入するため正式成果物だけを選択する
- 実行日を自動的に基準日へ使う案: 時刻・タイムゾーン依存で再現性を失うため採用しない

## 理由

公開契約を管理契約から分離し、許可項目だけを新規構築することで、内部情報の混入を構造・実装・検証の三層で防げます。非正規化により画面は検証済みの表示データだけを読み、Git差分では実際に画面へ渡る内容を日英とも確認できます。明示的な基準日と固定順序により、手編集や生成忘れもバイト比較で検出できます。
