## 1. 目的

本文書は、「まどぐちみまもり」の開発作業について、作業開始前の情報確認から、目的・要件整理、現行調査、設計、実装計画、実装・ローカル検証、レビュー、マージ、必要なproduction公開、公開後確認、完了整理までをPhase 0〜Phase 6の標準手順として定義する。

開発作業を一貫した手順で進めることで、利用者様が国・地方公共団体その他の公的機関・関係団体の公式情報・公式窓口へ安全かつ迅速に到達できるという「まどぐちみまもり」の目的を維持し、安全性、品質、設計と運用保守の維持可能性を確保する。

また、確認済み情報と未確認情報・推測を分離し、各Phaseの判断根拠、未解決事項、検証結果を明確にすることで、開発判断の再現性と追跡可能性を維持する。

## 2. 文書の位置付け

本文書は、正式運用移行後、Phase 0〜Phase 6の詳細な開始条件、入力情報、実施手順、成果物、完了条件、終了判定を定義する「開発作業標準フロー」の正本とする。

開発作業標準フローの管理・適用判断・変更種別・情報確認原則は `DEVELOPMENT_PROCESS_RULES.md` を正本とする。

第一版開発時の工程1〜工程13の計画と実績を記録した `DEVELOPMENT_PHASES.md` は歴史的文書であり、本文書のPhase 0〜Phase 6とは別の工程体系である。正式運用移行後の開発では、本文書のPhase 0〜Phase 6を標準フローとして使用する。

正式運用移行時には、`README.md` および `docs/README.md` を、これら正本文書への入口として利用する。

本文書は現在 `Draft` であり、本VersionではPhase 0〜Phase 4までの詳細本文を確定している。Phase 5〜Phase 6の詳細本文は現在設計中であり、すべての詳細本文を確定した後に関連文書との整合を確認し、正式運用へ移行する。

## 3. 適用ルール

本文書の適用判断は `DEVELOPMENT_PROCESS_RULES.md` に従う。

- **A. 標準フロー適用**：Phase 0〜Phase 6を実施する。
- **B. 軽微変更（簡略適用）**：影響範囲に応じて必要なPhase・確認のみ実施し、簡略適用と判断した理由を記録する。
- **C. 緊急対応**：復旧または安全確保を優先し、対応後に事後レビューを実施する。

作業開始時は変更種別を仮分類し、Phase 0で正式判断する。

適用判断の詳細、対象範囲、例外対応については `DEVELOPMENT_PROCESS_RULES.md` を正とする。

| Phase   | 名称                                         | 主な問い                                     |

| Phase 2 | 現行仕様・影響範囲・関連資料の調査           | 現在どうなっていて、何に影響するか           |

## 5. 全Phase共通ルール

### 5.1 情報の状態

情報は以下の状態を区別する。

- `確認済み`：判断に必要な範囲で実内容を確認した情報
- `未確認`：参照可能だが、まだ実内容を確認していない情報
- `参照不能`：必要な資料・情報へアクセスできない状態
- `不明`：現時点の情報では判断できない事項

推測・仮説は、確認済み情報とは明確に分離して記録する。

資料名、ファイル名、URL、存在そのものを確認しただけでは、実内容を確認済みとは扱わない。

### 5.2 Phase終了判定

各Phaseでは、以下の4種類の終了判定を使用する。

#### `PASS`

そのPhaseの完了条件を満たし、次Phaseへ進める状態。

#### `PASS WITH OPEN ITEMS`

未解決事項は残るが、以下を満たす場合。

- 未解決事項が明示されている
- 次Phaseへ進む安全性を損なわない
- 解消時期または確認時期が明確である

#### `STOP`

そのPhase内で追加確認・修正・再検討が必要な状態。

必要な対応後、同じPhaseで再判定する。

#### `ON HOLD`

追加対応を行っても現時点では次Phaseへ安全に進めないため、作業を意図的に保留する状態。

最低限、以下を記録する。

- 保留理由
- 不足情報・未解決事項
- 次Phaseへ進めない理由
- 再開条件

### 5.3 前Phaseへ戻る原則

後続Phaseで前提・要件・現行仕様・設計・計画に問題が判明した場合、実装や後続工程で無理に吸収せず、問題の発生元となるPhaseへ戻って再確認する。

基本的な戻り先は以下とする。

- 作業前提・参照情報・現在状態 → **Phase 0**
- 目的・要件・Scope → **Phase 1**
- 現行仕様・影響範囲 → **Phase 2**
- 採用する設計 → **Phase 3**
- 実装・テスト／確認計画 → **Phase 4**

前Phaseへ戻る場合も、現在存在するローカル変更やGit差分を勝手に破棄しない。

### 5.4 Scopeを勝手に拡大しない

各Phaseで別の改善候補・問題・技術的負債を発見しても、今回の目的とScopeへ自動的に追加しない。

必要に応じて、追加発見事項、将来対応候補、バックログ候補として分離する。

### 5.5 明示承認が必要な操作

実装開始、Gitブランチ作成・切替、commit、push、PR作成、PRマージ、productionデプロイ、revert、再デプロイ、作業ブランチ削除、既存差分破棄など、リポジトリ・本番環境・作業状態を変更する操作は、`AGENTS.md` および各Phaseの規定に従い、利用者の明示的な承認を得てから実施する。

## 6. Phase 0：作業開始前確認・情報参照・現状把握

### 6.1 目的

開発作業の検討を開始する前に、プロジェクト、変更目的、現在状態、関連資料、参照可能性を確認し、確認済み情報と未確認・参照不能・不明な情報を分離する。

そのうえで変更種別を正式に判断し、Phase 1以降の検討を安全に開始できる状態かを判定する。

Phase 0は、具体的な変更方法を設計するPhaseではない。

主な問いは、以下とする。

> **現在の情報と作業状態を踏まえて、安全に開発検討を開始できるか**

### 6.2 開始前の最低限入力情報

Phase 0を開始する前に、最低限、以下の8項目を揃える。

1. プロジェクト名
2. GitHubリポジトリ
3. ローカルのソース格納ディレクトリ
4. 変更種別（仮）
5. 変更概要
6. 目的
7. 関連資料
8. 開発開始前であること

この8項目は、`DEVELOPMENT_PROCESS_RULES.md` でPhase 0開始前の最低限入力情報として定義されている内容を正とする。

不足している場合は、Phase 0内で不足事項として明示する。

### 6.3 実施手順

#### 6.3.1 最低限入力情報の確認

6.2の8項目について、以下を確認する。

- 提示済み
- 未提示
- 内容不明

資料名やURLだけが提示されていても、その実内容まで確認したとは扱わない。

#### 6.3.2 作業環境・現在状態の確認

開発判断の前提となる現在状態を確認する。

ローカルGit状態を利用者または実行可能な開発環境で確認する場合は、最低限以下を確認対象とする。

\`\`\`sh
pwd
git branch --show-current
git status -s
git diff origin/main
ls -la
\`\`\`

確認する内容は以下とする。

- 対象リポジトリが正しいか
- 現在のブランチ
- 既存のローカル差分
- `origin/main` との差分
- 必要なファイル・ディレクトリの存在

想定外のブランチや既存差分がある場合は、勝手に変更・削除・破棄・stashしない。

Phase 0は現状確認のPhaseであるため、ここでは `git pull` など作業状態を変更する操作は行わない。

#### 6.3.3 関連資料の特定

今回の変更判断に必要な資料を特定する。

必要に応じて対象となるものは以下とする。

- `README.md`
- `AGENTS.md`
- `docs/README.md`
- `DEVELOPMENT_PROCESS_RULES.md`
- 関連する設計文書
- ADR
- コード
- 設定
- Googleスプレッドシート
- Pull Request / Issue
- production環境
- 外部公式資料
- その他今回の判断に必要な資料

毎回すべての文書を読む必要はない。

`docs/README.md` 等を入口として、今回の目的・変更内容に関係する正本文書を選択する。

#### 6.3.4 資料の実内容確認・情報状態の分類

選択した資料について、判断に必要な範囲で実内容を確認する。

情報は共通ルールに従い、以下へ分類する。

- `確認済み`
- `未確認`
- `参照不能`
- `不明`

推測・仮説は確認済み情報と分離する。

##### 利用者から提示されたローカル実行結果

利用者が `git status -s`、`git diff origin/main` などの実行結果を提示した場合は、

> **利用者が提示したローカル実行結果として確認済み**

と扱う。

これは、開発エージェント自身が利用者のローカルPCへ直接アクセスして確認したことを意味しない。

この区別を明示する。

#### 6.3.5 未確認・参照不能・不明事項の影響評価

確認できていない事項について、

> **この情報が未確認のままでもPhase 1へ安全に進めるか**

を評価する。

例えば、以下を区別する。

- 今回の判断へ影響しない軽微な未確認事項
- Phase 1以降で確認可能な事項
- Phase 1開始前に必ず確認が必要な事項

確認できない情報を、推測で補ってPhase 1へ進めない。

#### 6.3.6 変更種別の正式判断

作業開始時に仮分類した変更種別について、Phase 0で正式判断する。

変更種別は以下とする。

- **A. 標準フロー適用**
- **B. 軽微変更（簡略適用）**
- **C. 緊急対応**

判断基準の正本は `DEVELOPMENT_PROCESS_RULES.md` とする。

Aと判断した場合は、本文書のPhase 0〜Phase 6を標準として使用する。

Bの場合は、影響範囲に応じて必要なPhase・確認だけを行い、以下を記録する。

- 変更内容
- 簡略適用と判断した理由

Cの場合は、安全確保・復旧を優先し、対応後に事後レビューを実施する。

#### 6.3.7 Phase 0終了判定

確認した情報をもとに、以下のいずれかを判定する。

- `PASS`
- `PASS WITH OPEN ITEMS`
- `STOP`
- `ON HOLD`

詳細は6.6に従う。

#### 6.3.8 未解決事項の整理

Phase 0終了時に残っている事項を整理する。

最低限、以下を明示する。

- 未確認事項
- 参照不能事項
- 不明事項
- Phase 1以降へ引き継ぐ事項
- 判断への影響

#### 6.3.9 Phase 1への引き継ぎ整理

Phase 1へ進む場合、少なくとも以下を引き継ぐ。

- 変更概要
- 目的
- 正式な変更種別
- 確認した現在状態
- 確認済み関連資料
- 未確認・参照不能・不明事項
- Phase 1で考慮すべき制約・前提
- Phase 0の終了判定

### 6.4 成果物

Phase 0終了時には、最低限以下が整理されている状態とする。

- Phase 0開始前の8項目
- 現在の作業環境・Git状態
- 今回参照する資料
- 確認済み情報
- 未確認情報
- 参照不能情報
- 不明事項
- 正式な変更種別
- 未解決事項とその影響
- Phase 0終了判定
- Phase 1への引き継ぎ事項

専用Markdownファイルを毎案件で新規作成することは必須としない。

### 6.5 完了条件

以下を満たした場合にPhase 0を完了できる。

- Phase 0開始前の最低限入力情報を確認している
- 対象リポジトリ・作業状態を必要な範囲で確認している
- 今回必要な関連資料を特定している
- 判断に必要な資料の実内容を確認している
- 確認済み・未確認・参照不能・不明を区別している
- 推測を確認済み情報として扱っていない
- 未確認事項が判断へ与える影響を把握している
- 変更種別A/B/Cを正式判断している
- Phase 1へ引き継ぐ前提・未解決事項を整理している
- Phase 1へ安全に進めるか判断できる

### 6.6 終了判定

#### `PASS`

必要な現在状態・資料・前提を確認でき、未解決事項なくPhase 1へ安全に進める状態。

#### `PASS WITH OPEN ITEMS`

未解決事項はあるが、以下を満たす場合。

- 明示されている
- Phase 1開始を妨げない
- 安全な判断を損なわない
- 後続Phaseで確認できる

未解決事項を保持したままPhase 1へ引き継ぐ。

#### `STOP`

Phase 1へ進むために必要な確認が不足している状態。

例：

- 必須資料をまだ確認していない
- 現在のリポジトリ状態が不明
- 重要な前提情報が不足
- 変更種別を判断できない

`STOP` の場合はPhase 0内に留まり、不足情報の補完・再確認を行う。

再確認後、以下のいずれかへ再判定する。

- `PASS`
- `PASS WITH OPEN ITEMS`
- `ON HOLD`

#### `ON HOLD`

`STOP` 後に必要な確認・補完を行っても、以下のようなPhase 1開始に必要な条件が揃わず、現時点では安全にPhase 1へ進めない状態。

- 目的
- 必要資料
- 作業前提
- その他Phase 1開始に必要な条件

最低限以下を記録する。

- 保留理由
- 不足情報・不足前提
- Phase 1へ進めない理由
- 再開条件

##### ON HOLDから再開する場合

保留中に以下が変更されている可能性がある。

- リポジトリ
- 正本文書
- production
- 関連資料

そのため、Phase 1へ直接進まない。

再開時はPhase 0から再開し、現在状態を改めて確認する。

### 6.7 Phase 0で行わないこと

Phase 0では、以下を行わない。

- 具体的な解決方法の設計
- 採用する設計の決定
- UI詳細設計
- データ構造変更の決定
- 実装計画の確定
- コード変更
- データ変更
- Schema変更
- 文書変更
- 画像変更
- テストコード変更
- Gitブランチ作成・切替
- commit
- push
- PR作成
- デプロイ
- production変更

Phase 0はあくまで、

> **開発検討を安全に開始できる状態か確認するPhase**

とする。

## 7. Phase 1：目的・要件・対象範囲の整理

### 7.1 目的

Phase 1では、Phase 0で確認した現在状態・関連資料・変更目的を前提として、今回の開発で解決する問題、達成する目的、成功条件、要件、対象範囲、対象外範囲、制約、優先度を整理する。

このPhaseでは、具体的な実装方法、UI構造、データ構造、ファイル変更方法などの「解決手段」は確定しない。

主な問いは、以下とする。

> **何を、何のために、どこまで解決するのか**

Phase 1の目的は、後続Phaseで設計・調査・実装方法の検討が目的から逸脱しないための基準を確立することである。

### 7.2 開始条件

Phase 1は、Phase 0の終了判定が以下のいずれかである場合に開始できる。

- `PASS`
- `PASS WITH OPEN ITEMS`

`PASS WITH OPEN ITEMS` の場合は、Phase 0から引き継いだ未解決事項について、Phase 1の判断へ与える影響を継続して管理する。

Phase 0が以下の場合はPhase 1へ進まない。

- `STOP`
- `ON HOLD`

### 7.3 入力情報

Phase 1では、Phase 0から最低限以下を引き継ぐ。

- 変更概要
- 変更目的
- 正式な変更種別
- 確認した現在状態
- 確認済み関連資料
- 未確認事項
- 参照不能事項
- 不明事項
- 制約・前提
- Phase 0終了判定

必要に応じて、利用者から追加の要望・背景・制約を確認する。

### 7.4 実施手順

#### 7.4.1 現在の問題を整理する

まず、

> **現在、何が問題なのか**

を明確にする。

問題は、できるだけ現在状態として記述する。

例えば、

- 必要な情報へ到達しにくい
- 表示内容が現在の設計方針と一致していない
- 同じ作業を毎回手動で繰り返している
- 文書間でルールの位置付けが分かりにくい
- 利用者が誤認する可能性がある

など、「現在起きている問題」を整理する。

この段階では、

- ボタンを追加する
- JSONを変更する
- スクリプトを作る
- 新しいAPIを導入する

などの解決方法を問題そのものとして定義しない。

#### 7.4.2 開発目的を整理する

次に、

> **今回の開発によって、どのような状態を実現したいか**

を整理する。

目的は「実現したい状態」として記述し、具体的な実装方法と分離する。

例えば、

「画像を差し替える」

ではなく、

> 利用者がブラウザやSNS上で「まどぐちみまもり」を正しく識別できる状態にする

のように整理する。

目的が複数ある場合は、主目的と副目的を必要に応じて区別する。

#### 7.4.3 達成条件・成功条件を整理する

目的が達成されたと判断できる条件を整理する。

達成条件は、後続Phaseで検証可能な表現にする。

例えば、

- 対象ページで必要な情報へ到達できる
- 日本語版・英語版で要件を満たす
- 既存の安全方針を維持している
- 対象データに不整合がない
- 必要な手動運用を再現可能な形で実施できる

など。

ここでは具体的なテストファイルやコマンドまでは決めない。

具体的な検証方法はPhase 4で確定する。

#### 7.4.4 要件を整理する

今回の開発に必要な要件を、該当する範囲で整理する。

すべての分類を毎回必ず使用する必要はない。

##### 機能要件

利用者または運用者が何をできる必要があるか。

##### UI・UX・表現要件

表示、文言、導線、favicon、OGP、アクセシビリティなど、利用者から見える状態に関する要件。

##### 非機能要件

保守性、性能、可用性、互換性、再現性など、機能そのもの以外の要件。

##### 安全性要件

以下を含め、利用者・運用者・サービスを守るために維持すべき要件。

- 誤認防止
- プライバシー
- セキュリティ
- アクセシビリティ
- 公式性確認
- 情報の過剰転載防止
- 現行の安全設計を損なわないこと

安全性・プライバシー・誤認防止に関わる既存方針は、原則として高い優先度で扱う。

#### 7.4.5 In Scopeを整理する

今回の作業単位で変更・検討対象とする範囲を明確にする。

必要に応じて、以下の観点で整理する。

- 地域
- ページ
- データ
- 言語
- 機能
- 文書
- 運用・保守プロセス
- 検証・品質管理プロセス

該当しない分類を無理に記載する必要はない。

In Scopeは、

> **今回の目的を達成するために、この作業単位で扱うもの**

として定義する。

#### 7.4.6 Out of Scopeを整理する

今回の作業単位では扱わない事項を明確にする。

Out of Scopeは、

> 不要である

という意味ではなく、

> **今回の作業単位では実施しない**

という意味で使用する。

将来必要となる可能性がある事項も、今回対象外であればOut of Scopeとして記録できる。

Phase 1以降で新たな改善候補を発見しても、自動的にIn Scopeへ追加しない。

#### 7.4.7 制約・前提を整理する

設計や実装判断を制約する既存条件を整理する。

例えば、

- 現行のサイト目的・基本方針
- 既存の公開URL
- 日本語・英語対応
- 公開済みデータとの互換性
- GitHub Pagesの利用
- 手動運用として残す判断
- 外部サービスを追加しない方針
- 既存文書・ADRで確定済みのルール

など。

未確認の事項を制約として確定しない。

仮定が必要な場合は「前提」または「仮定」として確認済み情報から分離する。

#### 7.4.8 優先度を整理する

要件が複数ある場合は、必要に応じて以下で優先度を整理する。

- `Must`
- `Should`
- `Could`

##### `Must`

今回の目的達成、安全性、公開可否に不可欠な要件。

##### `Should`

可能な限り今回満たすべきだが、未達でも目的そのものを直ちに損なわない要件。

##### `Could`

余力がある場合に検討できる改善事項。

安全性、プライバシー、誤認防止、既存の重要な設計方針を守るための要件は、原則として `Must` として扱う。

#### 7.4.9 未解決事項を整理する

Phase 1で確定できない事項を明示する。

最低限、以下を整理する。

- 未解決事項
- なぜ現時点で確定できないか
- どのPhaseで確認・解消するか
- Phase 2へ進むことへの影響

未解決事項を暗黙の前提として扱わない。

#### 7.4.10 Phase 2で調査する事項を整理する

Phase 1で確定した目的・要件・Scopeから、

> **Phase 2で何を確認する必要があるか**

を整理する。

例えば、

- 現在どのファイルが対象機能を実装しているか
- どのデータが対象ページへ反映されるか
- 既存の検証手段があるか
- 日本語版・英語版の現在仕様
- productionと正本文書が一致しているか
- 対象変更がどこへ影響する可能性があるか

など。

ここでは調査対象を決めるだけで、解決方法は決定しない。

### 7.5 成果物

Phase 1終了時には、最低限以下が整理されている状態とする。

- 現在の問題
- 開発目的
- 達成条件・成功条件
- 要件
- In Scope
- Out of Scope
- 制約・前提
- 要件の優先度
- 未解決事項
- Phase 2で調査する事項
- Phase 1終了判定

専用Markdownファイルを毎案件で新規作成することは必須としない。

### 7.6 完了条件

以下を満たした場合にPhase 1を完了できる。

- 現在の問題を整理している
- 開発目的を明確にしている
- 目的と具体的な解決方法を分離している
- 達成条件・成功条件を整理している
- 必要な要件を整理している
- In Scopeを明確にしている
- Out of Scopeを明確にしている
- 必要な制約・前提を整理している
- 必要に応じて要件の優先度を整理している
- 未解決事項を明示している
- Phase 2で調査する事項を特定している
- Phase 2へ安全に進めるか判断できる

### 7.7 終了判定

#### `PASS`

問題、目的、要件、Scope、制約、成功条件が必要な範囲で確定し、未解決事項なくPhase 2へ進める状態。

#### `PASS WITH OPEN ITEMS`

未解決事項はあるが、以下を満たす場合。

- 未解決事項が明示されている
- Phase 2で確認可能である
- 現行調査を開始するための目的・Scopeが十分に明確である
- 安全性を損なわない

未解決事項をPhase 2へ引き継ぐ。

#### `STOP`

Phase 2で何を調査すべきか決められない程度に、目的・要件・Scopeが不足または矛盾している状態。

例えば、

- 開発目的が不明
- 解決方法だけが決まっていて問題が明確でない
- In ScopeとOut of Scopeが判断できない
- 重要な要件が未整理
- 成功条件が判断できない

`STOP` の場合はPhase 1内で追加整理・確認を行う。

必要に応じてPhase 0へ戻る。

#### `ON HOLD`

Phase 1内で必要な確認を行っても、目的・要件・Scopeを安全に確定できない状態。

最低限以下を記録する。

- 保留理由
- 未確定の目的・要件・Scope
- Phase 2へ進めない理由
- 再開条件

再開時にPhase 0の前提・関連資料・現在状態が変わっている可能性がある場合は、Phase 0から再確認する。

### 7.8 Phase 1で行わないこと

Phase 1では、以下を行わない。

- 具体的な実装方法の決定
- 採用する設計の決定
- 詳細UI設計
- データ構造・Schema変更の決定
- API・ライブラリ・サービス選定
- 変更ファイルの確定
- 実装順序の確定
- テストコードの詳細設計
- 具体的なテストケース・コマンドの確定
- コード変更
- データ変更
- 文書変更
- Git操作
- production変更

Phase 1はあくまで、

> **今回の開発で「何を、何のために、どこまで解決するか」を確定するPhase**

とする。

## 8. Phase 2：現行仕様・影響範囲・関連資料の調査

### 8.1 目的

Phase 2では、Phase 1で確定した問題、目的、要件、In Scope、Out of Scope、制約、成功条件を前提として、現在の仕様・実装・データ・運用・検証方法・公開状態を必要な範囲で調査する。

そのうえで、今回の変更によって影響を受ける可能性がある対象、依存関係、既存の制約、不整合、検証手段を明らかにする。

Phase 2では、確認した事実と推測を分離し、

> **現在どうなっていて、何に影響するか**

を明確にする。

このPhaseでは、具体的な変更方法、採用する設計、実装方法は決定しない。

### 8.2 開始条件

Phase 2は、Phase 1の終了判定が以下のいずれかである場合に開始できる。

- `PASS`
- `PASS WITH OPEN ITEMS`

`PASS WITH OPEN ITEMS` の場合は、Phase 1から引き継いだ未解決事項について、今回の調査対象や判断へ与える影響を継続して管理する。

Phase 1が以下の場合はPhase 2へ進まない。

- `STOP`
- `ON HOLD`

### 8.3 入力情報

Phase 2では、Phase 1から最低限以下を引き継ぐ。

- 現在の問題
- 開発目的
- 達成条件・成功条件
- 要件
- In Scope
- Out of Scope
- 制約・前提
- 要件の優先度
- 未解決事項
- Phase 2で調査する事項
- Phase 1終了判定

必要に応じて、Phase 0で確認した以下も参照する。

- 現在の作業環境・Git状態
- 確認済み関連資料
- 未確認情報
- 参照不能情報
- 不明事項
- 正式な変更種別

### 8.4 実施手順

#### 8.4.1 調査対象を選定する

Phase 1で整理した目的・要件・Scopeをもとに、今回調査する対象を選定する。

必要に応じて、以下を対象とする。

- `README.md`
- `AGENTS.md`
- `docs/README.md`
- `DEVELOPMENT_PROCESS_RULES.md`
- `DEVELOPMENT_STANDARD_FLOW.md`
- 関連設計文書
- ADR
- ソースコード
- データ
- Schema
- fixture
- テスト
- package scripts
- GitHub Actions / workflow
- preview成果物
- production成果物
- productionサイト
- Googleスプレッドシート等の管理資料
- 外部公式資料
- その他今回の目的・要件に直接関係する資料

毎回すべてを調査する必要はない。

今回の目的・要件・Scopeに関係するものを選択し、調査対象を必要以上に拡大しない。

#### 8.4.2 現行仕様を整理する

調査対象について、現在どのような仕様になっているかを確認する。

必要に応じて、以下の観点で整理する。

##### 利用者向け仕様

- ページ構成
- 導線
- 表示内容
- 文言
- URL
- 言語
- favicon
- OGP
- アクセシビリティ
- JavaScript有効・無効時の挙動
- その他利用者から見える仕様

##### データ仕様

- データ構造
- ID
- 参照関係
- locale構造
- 公開対象・非公開対象
- 管理情報と公開情報の分離
- Schema
- fixture
- 生成元データ

##### 実装仕様

- 対象ファイル
- 生成処理
- JavaScript
- CSS
- HTML
- スクリプト
- 外部ライブラリ
- 設定
- 依存関係

##### 運用仕様

- データ更新方法
- 手動確認
- TSV import
- production生成
- デプロイ
- 公開後確認
- Googleスプレッドシート等との連携
- その他保守作業

##### 品質管理仕様

- lint
- format
- test
- data validation
- docs validation
- public / site validation
- verify
- 手動ブラウザ確認
- 外部リンク確認
- その他既存の品質確認

##### 公開・インフラ仕様

必要な場合のみ、以下も確認する。

- GitHub Pages
- production URL
- custom domain
- HTTPS
- GitHub Actions
- workflow
- GA4
- sitemap
- その他公開に関係する構成

確認していないものを現在仕様として推測しない。

#### 8.4.3 正本文書・実装・公開状態の整合を確認する

必要に応じて、以下の間で現在状態が一致しているか確認する。

- 正本文書
- 設計文書
- ADR
- 実装
- 管理データ
- 生成成果物
- preview
- production
- 運用手順
- テスト・検証方法

一致していない場合は、推測でどちらかを正しいと決めず、

> **不整合あり**

として記録する。

必要に応じて以下を整理する。

- 何と何が一致していないか
- どの内容を確認済みか
- どちらが正しいか現時点で判断できるか
- Phase 3へ進む前に解消が必要か
- 今回のScopeへ影響するか

#### 8.4.4 現行の制約・不変条件を確認する

今回の変更でも維持する必要がある現行条件を確認する。

例えば、

- サイトの目的
- 公式発表そのものを転載しすぎない
- 速報サイトにしない
- 真偽判定・信頼性格付けを行わない
- 公式性は人が確認する
- 入力フォームを持たない
- 不要な外部API・自動取得を追加しない
- 日本語・英語の扱い
- 管理情報を公開成果物へ含めない
- 既存URL互換性
- JS非依存で維持すべき主要導線
- プライバシー上の制約
- 運用保守上維持すべき条件

など。

Phase 1の制約・安全要件と、現行実装上の不変条件を混同せず整理する。

#### 8.4.5 影響範囲を調査する

今回の変更によって影響する可能性がある対象を確認する。

必要に応じて、以下の観点を調査する。

- 利用者向けUI
- ページ
- URL / route
- 日本語版・英語版
- 公開データ
- 管理データ
- Schema
- fixture
- 生成処理
- HTML
- CSS
- JavaScript
- 画像・静的アセット
  - favicon
  - OGP画像
  - その他画像
  - CSS / JS等の静的ファイル
- preview成果物
- production成果物
- テスト
- validation
- 文書
- ADR
- Googleスプレッドシート等の外部管理資料
- 運用・保守手順
- GitHub Actions / workflow
- デプロイ
- GA4
- プライバシー
- アクセシビリティ
- 外部公式URL
- その他今回の要件に関係する対象

各対象は、確認結果に応じて例えば以下で整理する。

- `直接影響`
- `間接影響`
- `影響なし`
- `不明`

「影響なし」は、必要な確認を行った結果として判断する。

確認していない対象を自動的に「影響なし」としない。

#### 8.4.6 依存関係を整理する

影響対象同士の依存関係を確認する。

例えば、

管理データ
↓
生成処理
↓
公開JSON
↓
HTML
↓
production表示

のように、変更がどの経路を通って反映されるかを把握する。

必要に応じて以下を確認する。

- 生成元と生成先
- 参照元と参照先
- Schemaとデータ
- locale間の関係
- 共通コンポーネント・共通CSS
- スクリプト間依存
- previewとproductionの生成関係
- 管理資料とリポジトリ成果物の関係
- workflowとproduction公開の関係

ここでは依存関係を把握するだけで、変更方法は決定しない。

#### 8.4.7 既存テスト・検証・手動確認方法を調査する

今回の要件や影響範囲について、現在どの検証手段が存在するかを確認する。

必要に応じて、以下を確認する。

- `QUALITY_TOOLING.md`
- `package.json`
- テストコード
- fixture
- Schema
- validation script
- verify script
- GitHub Actions
- 手動確認手順
- preview確認方法
- production公開後確認方法

確認した検証手段について、

- 既存の仕組みで十分確認可能
- 既存の仕組みで一部確認可能
- 現在の仕組みでは確認できない

などを整理する。

Phase 2では、

> **現在、何をどの仕組みで確認できるか**

を調査する。

新しいテストや検証方法を具体的に設計するのは後続Phaseで行う。

##### テスト・検証に関するPhase境界

- **Phase 2**
  - 現在どの検証手段があるか
  - 何を確認できるか
  - 何が確認できないか

- **Phase 3**
  - 新しい設計について何を検証可能にする必要があるか

- **Phase 4**
  - 具体的にどのテスト、コマンド、手動確認を実施するか

- **Phase 5**
  - 実際にテスト・検証・確認を実施する

この境界を維持する。

#### 8.4.8 手動確認が必要な現在仕様を確認する

自動検証だけでは確認できない事項がある場合、その現在の確認方法を整理する。

例えば、

- ブラウザ表示
- PC / mobile
- 日本語 / 英語
- キーボード操作
- focus表示
- JavaScript無効
- CSS無効
- zoom
- favicon
- OGP
- コンソール
- 外部URL
- production実URL
- 公的機関サイトへの到達
- 実際の画面上のアクセシビリティ

など。

外部URLが現在到達可能か、productionで正しく表示されるか等は、自動テストだけでは十分でない場合がある。

Phase 2では、現在どのような手動確認が必要かを把握する。

#### 8.4.9 既知の不整合・技術的負債・関連発見事項を整理する

調査中に、既存の不整合や技術的負債を発見した場合は記録する。

ただし、今回の目的・Scopeと直接関係しない問題を、自動的に今回の作業対象へ追加しない。

以下を区別する。

- 今回の設計判断へ直接影響する事項
- 今回の変更により悪化する可能性がある事項
- 今回とは無関係だが発見した事項

無関係な事項は、必要に応じて将来対応候補・バックログ候補として分離する。

#### 8.4.10 未解決事項・追加調査事項を整理する

Phase 2で確認できなかった事項を整理する。

最低限、以下を明示する。

- 未確認事項
- 参照不能事項
- 不明事項
- 追加調査が必要な事項
- Phase 3の設計判断への影響
- Phase 3へ進む前に解消が必要か

確認できない情報を、設計上の事実として扱わない。

#### 8.4.11 Phase 3の設計論点を整理する

Phase 2の調査結果から、

> **Phase 3で何を設計判断する必要があるか**

を整理する。

例えば、

- 現行仕様のどこを維持する必要があるか
- どの要件について設計判断が必要か
- どの不整合を解消する必要があるか
- 互換性をどう扱う必要があるか
- データ・UI・運用のどこに設計論点があるか
- 何を検証可能にする必要があるか

など。

ここでは論点を整理するだけで、採用する設計は決定しない。

### 8.5 成果物

Phase 2終了時には、最低限以下が整理されている状態とする。

- 調査対象
- 現行仕様
- 正本文書・実装・公開状態の整合状況
- 現行の制約・不変条件
- 影響範囲
- 影響対象ごとの状態
- 依存関係
- 既存テスト・検証方法
- 既存の手動確認方法
- 現在検証できること
- 現在検証できないこと
- 既知の不整合
- 関連する技術的負債
- 未解決事項
- 追加調査事項
- Phase 3の設計論点
- Phase 2終了判定

専用Markdownファイルを毎案件で新規作成することは必須としない。

### 8.6 完了条件

以下を満たした場合にPhase 2を完了できる。

- Phase 1の目的・要件・Scopeに基づいて調査している
- 必要な現行仕様を実内容から確認している
- 確認済み情報と推測を分離している
- 正本文書・実装・公開状態の必要な整合確認を行っている
- 現行の制約・不変条件を整理している
- 影響範囲を必要な範囲で確認している
- 影響対象の依存関係を整理している
- 既存のテスト・検証・手動確認方法を確認している
- 現在検証できること・できないことを整理している
- 既知の不整合・関連する技術的負債を整理している
- Scope外の発見事項を勝手に今回の対象へ追加していない
- 未解決事項・追加調査事項を明示している
- Phase 3で設計する論点を整理している
- Phase 3へ安全に進めるか判断できる

### 8.7 終了判定

#### `PASS`

Phase 3で設計判断を行うために必要な現行仕様、影響範囲、制約、依存関係、検証状況を十分確認でき、未解決事項なくPhase 3へ進める状態。

#### `PASS WITH OPEN ITEMS`

未解決事項はあるが、以下を満たす場合。

- 未解決事項が明示されている
- Phase 3の設計判断を安全に開始できる
- 未解決事項を推測で補完する必要がない
- 後続Phaseで確認可能である
- 安全性・重要要件の判断を損なわない

未解決事項をPhase 3へ引き継ぐ。

#### `STOP`

Phase 3で安全に設計判断を行うために必要な調査が不足している状態。

例えば、

- 現行仕様が十分確認できていない
- 重要な影響範囲が不明
- 正本文書と実装の不整合が未確認
- 重要な依存関係が不明
- 現在の検証方法が確認できていない
- 調査結果が矛盾している

`STOP` の場合はPhase 2内で追加調査を行う。

調査中に、問題がPhase 1の目的・要件・Scopeにあると判明した場合はPhase 1へ戻る。

作業前提・参照資料・現在状態に問題がある場合はPhase 0へ戻る。

#### `ON HOLD`

必要な調査を行っても、Phase 3で安全に設計判断するための情報を取得できない状態。

最低限以下を記録する。

- 保留理由
- 未確認・参照不能・不明事項
- Phase 3へ進めない理由
- 再開条件

再開時にリポジトリ、資料、production等の現在状態が変化している可能性がある場合は、Phase 0から再確認する。

### 8.8 Phase 2で行わないこと

Phase 2では、以下を行わない。

- 採用する設計の決定
- 解決方法の確定
- UI変更内容の決定
- データ構造変更の決定
- Schema変更方針の決定
- API・ライブラリ・外部サービスの採用決定
- 具体的な変更ファイルの確定
- 実装順序の確定
- 新規テストケースの詳細設計
- 新しい検証コマンドの確定
- コード変更
- データ変更
- Schema変更
- 文書変更
- 画像変更
- テストコード変更
- Git操作
- production変更
- デプロイ

Phase 2はあくまで、

> **現在どうなっていて、何に影響するかを事実ベースで確認するPhase**

とする。

## 9. Phase 3：設計・安全性・整合性の検討と確定

### 9.1 目的

Phase 3では、Phase 1で確定した目的・要件・Scopeと、Phase 2で確認した現行仕様・影響範囲・制約・依存関係・検証状況を前提として、今回の変更をどのように実現するかを検討し、採用する設計を確定する。

必要に応じて複数の設計候補を比較し、目的達成、安全性、正確性、プライバシー、セキュリティ、コスト、複雑性、保守性、運用負荷、変更容易性、障害時の復旧可能性などを総合的に評価する。

Phase 3の主な問いは、

> **目的・要件を、安全かつ維持可能な形でどのように実現するか**

とする。

**目的・Must要件・安全性を満たしたうえで、現在の規模と将来の合理的な変更を考慮し、必要十分な設計を選ぶ。**

このPhaseでは設計を確定するが、具体的な実装作業やテストコード作成は行わない。

### 9.2 開始条件

Phase 3は、Phase 2の終了判定が以下のいずれかである場合に開始できる。

- `PASS`
- `PASS WITH OPEN ITEMS`

`PASS WITH OPEN ITEMS` の場合は、Phase 2から引き継いだ未解決事項について、設計判断へ与える影響を継続して管理する。

Phase 2が以下の場合はPhase 3へ進まない。

- `STOP`
- `ON HOLD`

### 9.3 入力情報

Phase 3では、最低限以下を引き継ぐ。

#### Phase 1から

- 現在の問題
- 開発目的
- 達成条件・成功条件
- 要件
- In Scope
- Out of Scope
- 制約・前提
- 要件の優先度

#### Phase 2から

- 現行仕様
- 正本文書・実装・公開状態の整合状況
- 現行の制約・不変条件
- 影響範囲
- 依存関係
- 既存テスト・検証方法
- 既存の手動確認方法
- 現在検証できること・できないこと
- 既知の不整合
- 関連する技術的負債
- 未解決事項
- Phase 3の設計論点

### 9.4 実施手順

#### 9.4.1 設計論点を整理する

Phase 2で整理した設計論点をもとに、

> **今回、何を設計判断する必要があるか**

を明確にする。

例えば、

- 現行仕様のどこを維持するか
- どこを変更する必要があるか
- UIをどう扱うか
- データ構造をどう扱うか
- 運用手順をどう扱うか
- 既存データとの互換性をどう扱うか
- 自動化する範囲と人手で残す範囲をどう分けるか
- 何を検証可能にする必要があるか

など。

設計論点を整理する前に、具体的な実装方法へ飛ばない。

#### 9.4.2 維持すべき条件を再確認する

設計候補を検討する前に、変更後も維持しなければならない条件を確認する。

最低限、以下を参照する。

- Phase 1で確定した目的・要件・安全性要件
- Phase 2で確認した現行の制約・不変条件
- `AGENTS.md`
- `README.md`
- 関連する設計文書
- ADR
- その他今回の設計に関係する正本文書

設計候補がこれらと矛盾する場合は、そのまま採用しない。

既存ルール自体を変更する必要がある場合は、それを別の設計論点として明示する。

#### 9.4.3 設計候補を整理する

必要に応じて、複数の設計候補を整理する。

ただし、

> **必ず3案出す**

など、形式的に候補数を固定しない。

合理的な候補が1つしかない場合は、無理に別案を作らなくてよい。

複数案が存在する場合は、それぞれについて、

- 何を変更する案か
- 何を維持する案か
- 目的をどう達成するか
- 主な利点
- 主な欠点
- リスク
- 既存仕様への影響

を整理する。

#### 9.4.4 設計候補を比較する

設計候補は、必要な範囲で以下の観点から比較する。

すべての項目を毎回同じ重みで評価する必要はない。

今回の目的・要件・変更内容に応じて、重要度を判断する。

##### A. 目的達成

###### 目的を達成できるか

最優先で確認する。

- Phase 1の開発目的を達成できるか
- 成功条件を満たせるか
- `Must` 要件を満たせるか

目的を達成できない案は、他の観点で優れていても原則採用しない。

##### B. 情報の正確性・誤認防止

###### 掲載情報の正確性を損なわないか

特に「まどぐちみまもり」では重要な観点とする。

例えば、

- 正しい公式情報・公式窓口へ案内できるか
- 誤った団体・URL・地域・対象を表示する可能性がないか
- 管理データと公開データの対応を維持できるか
- 自動化によって人の公式性確認を誤って省略しないか
- 古い情報や別地域の情報を誤って表示しないか

を確認する。

###### 利用者の誤認を増やさないか

- 公式サイトそのものと誤認されないか
- 真偽判定・信頼性格付けを行っているように見えないか
- 自動処理結果を人が確認済みの事実と誤認させないか

などを確認する。

##### C. 安全性

###### プライバシー

以下を確認する。

- 新たな個人情報を取得しないか
- 不要なログを残さないか
- 外部サービスへ情報を送信しないか
- 管理情報・内部情報を公開成果物へ含めないか
- GA4等の既存プライバシー方針へ影響しないか

###### セキュリティ

以下を確認する。

- 新しい入力値を受け付けるか
- URL parameter等の外部入力が増えるか
- DOM操作やHTML生成に新しいXSS経路を作らないか
- 外部JavaScript・ライブラリ・APIを追加するか
- 新しい権限が必要になるか
- secret・token等を扱う必要があるか
- 公開してはいけない情報を成果物へ含めないか

現在の静的サイト・入力なしという構成は攻撃面を小さくしているが、

> **静的サイトだから脆弱性が発生しない**

とは扱わない。

変更によって新しい攻撃面が増えないか確認する。

##### D. コスト

###### 金銭的コスト

- AWS・GitHub・外部API等の利用料が増えないか
- 有料サービスへの依存が増えないか
- 将来利用者増加時にコストが急増しないか

###### 維持コスト

金額だけでなく、

- 開発時間
- 保守時間
- 手動確認時間
- 障害対応時間

もコストとして評価する。

##### E. 複雑性

###### 実装・設計が必要以上に複雑にならないか

- 現在の目的に対して過剰な仕組みを導入していないか
- 新しい抽象化・層・依存関係が本当に必要か
- 単純な変更を大規模な仕組みにしていないか

を確認する。

「将来使うかもしれない」だけを理由に、現在不要な複雑性を追加しない。

##### F. 疎結合・変更容易性

###### 疎結合になっているか

必要に応じて、

- データ
- UI
- 生成処理
- validation
- 運用
- 外部サービス

が必要以上に強く依存していないか確認する。

ある部分を変更しただけで、無関係な多数の部分を変更しなければならない構造は避ける。

###### 変更可能な設計になっているか

- 地域追加
- 言語追加
- 案内カード追加
- 運用変更
- validation追加

など、想定される将来変更を必要以上に困難にしないか確認する。

ただし、将来拡張のために現在不要な機能を先行実装しない。

##### G. 拡張性

###### 将来の合理的な拡張を妨げないか

必要に応じて、

- 全国展開
- 地域追加
- 分野追加
- 言語追加
- 品質管理強化
- 運用自動化

などへの影響を確認する。

拡張性は、

> **何でもできる汎用設計**

を目指すことではない。

現時点で合理的に予測できる変更を、不必要に困難にしないことを目的とする。

##### H. 運用・保守性

###### 運用効率が悪化しないか

- 更新手順が増えすぎないか
- 同じ情報を複数箇所へ入力する必要がないか
- 確認工程が重複しないか
- 誤操作しやすい工程が増えないか

を確認する。

###### 人の手作業が増えすぎないか

人手確認そのものが必要な工程と、機械的に自動化できる工程を区別する。

特に、

> **人が判断すべきことを自動化する**

ことと、

> **人の判断を支援するため機械的作業を自動化する**

ことを分ける。

「公式性の最終確認」のように人の判断が重要な工程は、効率だけを理由に削除しない。

##### I. 保守性・可読性

以下を確認する。

- 他の開発者・将来の自分が理解できるか
- 設計意図を説明できるか
- データの流れを追跡できるか
- 変更箇所を特定しやすいか
- 既存ルールと矛盾しないか
- 必要な文書を維持できるか

##### J. 検証可能性

以下を確認する。

- 正しく動いていることを確認できる設計か
- 自動テスト可能か
- validation可能か
- 手動確認が必要な箇所を特定できるか
- production公開後に正しい状態を確認できるか

「動いているはず」しか確認方法がない設計は避ける。

##### K. 障害・復旧可能性

###### システム障害発生時に復旧できるか

必要に応じて以下を確認する。

- 障害原因を特定できるか
- 正常な状態へ戻せるか
- データを失わないか
- 再生成できるか
- 再デプロイできるか
- 外部サービス停止時にどうなるか
- 一部の失敗が全体障害へ波及しないか

特に生成物については、

> **正本から再生成できる**

状態を維持することを重視する。

###### 変更を戻せるか

必要に応じて、

- rollback
- revert
- 再生成
- 再デプロイ

が可能かを確認する。

ただし、具体的な復旧手順の実装はPhase 4以降で整理する。

##### L. 現行仕様との整合性

以下を確認する。

- 現行データとの互換性
- 現在のURL
- 日本語・英語
- preview / production
- 生成処理
- Schema
- validation
- 運用フロー

などと矛盾しないか。

既存仕様を変更する場合は、それを意図的な変更として明示する。

##### M. 将来への影響

以下を確認する。

- 技術的負債を大きく増やさないか
- 特定のツール・サービスへ不要にロックインしないか
- 将来変更時の影響範囲を不必要に広げないか
- 現時点では不要な恒久的制約を作らないか

#### 9.4.5 設計候補の比較結果を整理する

複数候補がある場合は、必要に応じて比較表などで整理する。

例えば、

| 観点         | 案A | 案B |
| ------------ | --- | --- |
| 目的達成     | ○   | ○   |
| 正確性       | ○   | △   |
| プライバシー | ○   | ○   |
| セキュリティ | ○   | △   |
| 金銭コスト   | ○   | △   |
| 複雑性       | ○   | △   |
| 運用負荷     | ○   | △   |
| 変更容易性   | ○   | ○   |
| 検証可能性   | ○   | ○   |
| 復旧可能性   | ○   | △   |

のように整理できる。

ただし、単純な点数合計だけで採用案を決めない。

特に以下は、他の利点で相殺しない。

- 目的を達成できない
- `Must` 要件を満たさない
- 重大な安全性問題
- 重大なプライバシー問題
- 重大なセキュリティ問題
- 重大な情報正確性・誤認リスク

#### 9.4.6 採用する設計を確定する

比較結果をもとに、採用する設計を明確にする。

必要に応じて以下を整理する。

##### 機能設計

- 何をできるようにするか
- 既存機能をどう維持するか

##### UI・UX・表現設計

- 何を表示するか
- 導線
- 文言
- favicon
- OGP
- アクセシビリティ

##### データ設計

- データの責務
- 生成元・生成先
- ID・参照関係
- locale
- Schemaとの関係

##### 運用・保守設計

- 人が行う作業
- 自動化する作業
- 確認責任
- 更新方法
- 障害時の基本方針

##### 検証・品質設計

- どの種類の品質を担保する必要があるか
- 何を自動検証可能にするか
- 何を手動確認する必要があるか

この段階では、具体的なファイル変更一覧、コマンド、テストケースまでは確定しない。

#### 9.4.7 安全性・プライバシー・セキュリティ・誤認防止レビュー

採用する設計について、実装計画へ進む前にレビューする。

最低限、今回該当する以下を確認する。

##### 情報安全性

- 掲載情報の正確性を損なわないか
- 人の公式性確認を維持できるか
- 内部管理情報が公開されないか

##### 誤認防止

- 公式サイトと誤認させないか
- 速報・真偽判定・格付けを行うように見えないか
- 自動処理結果を確定事実として見せないか

##### プライバシー

- 不要な情報収集が増えないか
- 不要な外部送信がないか
- 既存のプライバシー方針を維持できるか

##### セキュリティ

- 新しい入力経路
- XSS
- 外部script
- 外部API
- dependency
- permission
- secret
- 公開範囲
- HTTPS
- その他攻撃面

##### アクセシビリティ

変更により、

- キーボード操作
- focus
- zoom
- JSなし
- CSSなし
- 多言語表示

等を不必要に損なわないか。

#### 9.4.8 全体整合性を確認する

採用する設計について、必要に応じて以下の整合を確認する。

- 日本語 / 英語
- 管理データ
- 公開データ
- Schema
- fixture
- HTML
- CSS
- JavaScript
- 画像・静的アセット
- preview
- production
- README
- 設計文書
- ADR
- Googleスプレッドシート
- 運用手順
- テスト
- validation
- privacy
- GA4
- GitHub Actions / workflow

「一箇所を変更すれば終わり」と思い込まず、Phase 2で確認した依存関係をもとに評価する。

#### 9.4.9 後方互換性・移行影響を確認する

該当する場合は以下を確認する。

- 既存データをそのまま利用できるか
- migrationが必要か
- 既存URLが変わるか
- 既存利用者への影響
- production成果物との互換性
- 古いデータ・成果物との共存
- rollback可能性

影響がない場合も、必要な確認を行った結果として「影響なし」と判断する。

#### 9.4.10 検証要件を確定する

Phase 3では、

> **採用する設計が正しいことを確認するために、何を検証可能にする必要があるか**

を整理する。

例えば、

- 必要なデータだけが公開されること
- 日本語・英語で同じ設計条件を満たすこと
- 不正データをvalidationで検出できること
- 主要導線がJSなしでも利用できること
- favicon / OGPが意図した成果物になること
- 管理情報がproductionへ出ないこと

など。

ここでは、

- 具体的なテストファイル
- テストケース名
- コマンド
- 手動確認手順

までは決めない。

それらはPhase 4で確定する。

#### 9.4.11 リスク・未解決事項を整理する

採用する設計について残るリスクを明示する。

最低限、必要に応じて以下を整理する。

- リスク内容
- 発生可能性
- 発生した場合の影響
- 対応方針
- Phase 4以降で確認する事項
- 現時点で許容可能か

未解決事項がある場合は、

- 未解決理由
- いつ解消するか
- 次Phaseへ進む影響

も整理する。

#### 9.4.12 ADR・文書化の必要性を判断する

今回の設計判断について、

- 将来なぜこの方式を選んだか確認する必要がある
- 複数案から重要な選択を行った
- 将来変更への制約になる
- セキュリティ・プライバシー・運用方針に影響する
- 既存方針を変更する

場合は、ADRまたは設計文書への記録が必要か判断する。

このPhaseでは記録の必要性と内容を確定し、実際の文書更新はPhase 5で行う。

### 9.5 成果物

Phase 3終了時には、最低限以下が整理されている状態とする。

- 設計論点
- 維持すべき条件
- 設計候補
- 設計候補の比較結果
- 採用する設計
- 採用理由
- 情報正確性レビュー結果
- 安全性レビュー結果
- プライバシーレビュー結果
- セキュリティレビュー結果
- 誤認防止レビュー結果
- 整合性確認結果
- 後方互換性・移行影響
- 検証要件
- リスク
- 未解決事項
- ADR・文書化要否
- Phase 3終了判定

### 9.6 完了条件

以下を満たした場合にPhase 3を完了できる。

- Phase 1の目的・要件・Scopeに基づいて設計している
- Phase 2の現行仕様・影響範囲・制約を反映している
- 必要な設計候補を検討している
- 目的達成を最優先に比較している
- 掲載情報の正確性・誤認リスクを確認している
- 安全性・プライバシー・セキュリティを確認している
- コスト・複雑性・保守性を確認している
- 疎結合・変更容易性・合理的な拡張性を確認している
- 運用効率・人手作業への影響を確認している
- 障害時の復旧可能性を確認している
- 採用する設計と採用理由を明示している
- 必要な整合性確認を行っている
- 後方互換性・移行影響を確認している
- 検証要件を整理している
- リスク・未解決事項を明示している
- ADR・文書化要否を判断している
- Phase 4へ安全に進めるか判断できる

### 9.7 終了判定

#### `PASS`

採用する設計が確定し、安全性・整合性・検証要件を含めてPhase 4へ進むために必要な設計判断が完了している状態。

#### `PASS WITH OPEN ITEMS`

未解決事項はあるが、

- 採用する設計は確定している
- 安全性を損なわない
- Phase 4で実装計画を作成できる
- 未解決事項が明示されている
- 解消するPhase・時期が分かっている

場合。

#### `STOP`

例えば、

- 目的を満たす設計が決まらない
- `Must` 要件を満たせない
- 重大な安全性問題がある
- 重大なプライバシー・セキュリティ問題がある
- 重要な現行仕様が不足している
- 候補比較に必要な情報が足りない
- 整合性を確認できない
- 検証不可能な設計になっている

場合。

問題の発生元に応じて、Phase 0〜2へ戻る。

#### `ON HOLD`

必要な設計検討を行っても、安全かつ実現可能な設計を確定できない状態。

最低限、

- 保留理由
- 未解決の設計論点
- Phase 4へ進めない理由
- 再開条件

を記録する。

### 9.8 Phase 3で行わないこと

Phase 3では以下を行わない。

- コード変更
- データ変更
- Schema変更
- HTML / CSS / JavaScript変更
- 画像変更
- 文書変更
- テストコード変更
- production変更
- デプロイ
- commit
- push
- PR作成
- PRマージ
- 具体的なテストケースの実装
- 具体的な実装順序の確定
- 実装作業

Phase 3はあくまで、

> **目的・要件を、安全かつ維持可能な形で実現する設計を確定するPhase**

とする。

## 10. Phase 4：実装計画・テスト／確認計画の確定

### 10.1 目的

Phase 4では、Phase 3で確定した採用する設計、安全性・プライバシー・セキュリティ・誤認防止レビュー、整合性確認、検証要件を前提として、実装・テスト・確認を安全かつ再現可能に進めるための具体的な計画を確定する。

Phase 4では、

- 何を変更するか
- 何を変更しないか
- どの順番で実装するか
- どの単位で作業するか
- どの自動テスト・validationを実施するか
- どの手動確認を実施するか
- セキュリティ上何を確認するか
- 各要件をどの方法で検証するか
- 文書・生成物・公開影響をどう扱うか
- 失敗時にどう停止・戻るか

を具体化する。

Phase 4の主な問いは、

> **何を変更し、どの順番で実現し、どう検証するか**

とする。

Phase 4は実装前の最終計画Phaseであり、このPhaseではコード・データ・文書その他の成果物を変更しない。

### 10.2 開始条件

Phase 4は、Phase 3の終了判定が以下のいずれかである場合に開始できる。

- `PASS`
- `PASS WITH OPEN ITEMS`

`PASS WITH OPEN ITEMS` の場合は、Phase 3から引き継いだ未解決事項について、実装計画・検証計画へ与える影響を明示して管理する。

Phase 3が以下の場合はPhase 4へ進まない。

- `STOP`
- `ON HOLD`

採用する設計が確定していない状態で、実装ファイル・実装順序・テスト方法だけを先に決めない。

### 10.3 入力情報

Phase 4では、最低限以下を引き継ぐ。

#### Phase 1から

- 開発目的
- 達成条件・成功条件
- 要件
- In Scope
- Out of Scope
- 制約・前提
- 要件の優先度

#### Phase 2から

- 現行仕様
- 影響範囲
- 依存関係
- 既存テスト・検証方法
- 既存の手動確認方法
- 現在検証できること・できないこと

#### Phase 3から

- 採用する設計
- 採用理由
- 維持すべき条件
- 安全性レビュー結果
- プライバシーレビュー結果
- セキュリティレビュー結果
- 誤認防止レビュー結果
- 整合性確認結果
- 後方互換性・移行影響
- 検証要件
- リスク
- 未解決事項
- ADR・文書化要否
- Phase 3終了判定

### 10.4 実施手順

#### 10.4.1 実装対象を整理する

採用する設計を実現するために、変更が必要な対象を具体化する。

必要に応じて以下を整理する。

- コード
- データ
- Schema
- fixture
- HTML
- CSS
- JavaScript
- 画像・静的アセット
- 生成処理
- validation
- test
- 文書
- ADR
- workflow
- 外部管理資料
- その他必要な対象

ファイル・ディレクトリが現時点で確認済みであれば、具体的なパスまで記載してよい。

ただし、実際に確認していないファイル名・パスを推測で確定しない。

不明な場合は、

- 対象機能
- 対象責務
- Phase 5開始時に確認する必要がある事項

として明示する。

#### 10.4.2 変更しない対象を整理する

今回の実装で意図的に変更しない対象を明示する。

例えば、

- Out of Scopeの機能
- 既存URL
- 既存データ構造
- production設定
- GA4
- privacy policy
- 日本語版または英語版の特定領域
- 外部サービス
- 既存の人手確認工程

など。

「変更しないもの」を明示することで、実装中のScope拡大を防ぐ。

Phase 5で対象外の問題を発見しても、自動的に修正対象へ追加しない。

#### 10.4.3 実装順序と依存関係を整理する

Phase 2で確認した依存関係とPhase 3で確定した設計をもとに、安全な実装順序を決める。

例えば、

1. 正本データ・Schema
2. 生成処理
3. validation
4. UI
5. test
6. 文書
7. 生成成果物

など、依存関係に沿って順序を決める。

ただし、毎回この順番を固定しない。

今回の設計に最も適した順序を選ぶ。

##### 生成成果物を扱う場合

生成可能な成果物は、原則として生成元・正本を変更して再生成する。

> **生成成果物を直接編集して正本との差異を作らない。**

生成成果物に問題が見つかった場合は、原則として生成元・生成処理・データ・設定のどこに原因があるか確認する。

#### 10.4.4 実装単位・PR単位を整理する

必要に応じて、今回の作業をどの単位で実装・レビューするか整理する。

例えば、

- 1つのPRで完結させる
- データ基盤とUIを分割する
- 設計文書と実装を分ける
- migrationと機能変更を分ける

など。

ただし、

> **形式的にPRを細分化しない。**

以下を基準に判断する。

- 1つの変更目的としてレビュー可能か
- 依存関係が強いか
- 安全に分割できるか
- 途中状態が危険にならないか
- rollback・原因切り分けがしやすいか
- レビュー可能な大きさか

単純な変更を、不必要に複数PRへ分割しない。

#### 10.4.5 テスト計画を具体化する

Phase 3で確定した検証要件について、Phase 5でどのように確認するかを具体化する。

必要に応じて以下を整理する。

##### 既存テスト

- どの既存テストで確認できるか
- そのままで十分か
- regression確認として何を利用するか

##### 新規テスト

新しい要件を既存テストで十分確認できない場合は、どの種類のテストを追加するか整理する。

例えば、

- 正常系
- 異常系
- 境界値
- 不正データ
- 欠損データ
- locale差異
- Schema
- 生成結果
- validation
- fallback
- 互換性

など。

必要に応じて、

- fixture
- mock
- test data
- expected result

についても計画する。

Phase 4ではテストケースを具体化できるが、テストコードそのものは実装しない。

#### 10.4.6 自動検証計画を確定する

今回の変更で必要な自動検証コマンドを整理する。

Phase 2で確認した既存の品質ツールをもとに、必要に応じて、

- lint
- format
- test
- fixture validation
- docs validation
- data validation
- public validation
- site validation
- verify
- その他対象固有のvalidation

を選択する。

##### 全変更共通の必須検証

「まどぐちみまもり」の標準フローでは、変更内容にかかわらずPhase 5で以下を必須とする。

1. `npm run validate:data`
2. `npm run check`

**この順序で実行し、両方の成功をPhase 5完了条件とする。**

個別のテスト・validationに成功していても、この2つを省略しない。

`npm run check` に含まれる検証と個別コマンドが重複する場合でも、必要な局所確認を先に実施したうえで、最後に全体確認として実行する。

#### 10.4.7 手動確認計画を確定する

自動テストだけでは十分確認できない要件について、Phase 5で行うローカル手動確認を整理する。

必要に応じて以下を対象とする。

- PC表示
- mobile表示
- 日本語
- 英語
- keyboard操作
- focus表示
- zoom
- JavaScript無効時
- CSS無効時
- favicon
- OGP
- console
- 404
- 外部リンク
- アクセシビリティ
- layout
- production相当の生成結果
- その他利用者向け表示

##### 自動「サイト検証」と手動ブラウザ確認を区別する

例えば、

- `validate:site`
- `verify:site`

のような自動検証と、

- ブラウザを実際に開く
- 画面を目視する
- keyboardで操作する
- consoleを確認する

といった手動確認は別物として扱う。

自動検証成功だけを理由に、必要なブラウザ確認を省略しない。

#### 10.4.8 セキュリティ確認計画を確定する

Phase 3のセキュリティレビュー結果をもとに、Phase 5で何を確認するか具体化する。

今回の変更内容に応じて、例えば以下を確認対象とする。

- 新しい外部入力
- query parameter
- DOM操作
- HTML生成
- escaping
- XSS
- 外部JavaScript
- dependency
- 外部API
- permission
- secret
- token
- 内部情報の露出
- 公開ファイル
- HTTPS
- CSP等の関連設定
- 不要な権限・通信

静的サイト・入力フォームなしの場合でも、

> **変更によって新しい攻撃面を作っていないこと**

を必要に応じて確認する。

#### 10.4.9 要件と検証方法を対応付ける

Phase 1の要件・成功条件と、Phase 4で決めた検証方法を対応付ける。

例えば、

| 要件・成功条件                 | 検証方法                           |
| ------------------------------ | ---------------------------------- |
| 日本語・英語で正しく表示される | 自動生成確認＋ローカルブラウザ確認 |
| 不正データを公開しない         | Schema / validation / test         |
| 管理情報を公開しない           | 自動テスト＋生成成果物確認         |
| keyboardで利用できる           | 手動keyboard確認                   |
| faviconが正しい                | 生成物確認＋ブラウザ確認           |

など。

重要なのは、

> **すべてのMust要件・安全性要件について、どの方法で確認するか説明できる状態にすること**

とする。

検証方法のないMust要件を残さない。

#### 10.4.10 文書更新計画を整理する

今回の変更に伴って更新が必要な文書を整理する。

必要に応じて、

- `README.md`
- `AGENTS.md`
- `docs/README.md`
- 設計文書
- ADR
- 運用手順
- マニュアル
- privacy policy
- その他関連文書

を対象とする。

以下を区別する。

- 実装と同じPRで更新する
- 別PRで更新する
- 更新不要
- Phase 6で最終整合確認のみ行う

文書更新が必要なのに、実装完了後まで無計画に残さない。

#### 10.4.11 生成・移行・公開影響を整理する

該当する場合は以下を整理する。

##### 生成

- 何を再生成するか
- 生成元は何か
- 生成成果物は何か
- 差分をどう確認するか

##### migration

- 既存データ変更が必要か
- 一括変換が必要か
- backward compatibilityをどう維持するか
- migration失敗時にどう扱うか

##### production公開影響

- production成果物が変わるか
- デプロイが必要か
- production公開不要か
- workflow実行が必要か
- 公開後に何を確認する必要があるか

実際のmerge・デプロイ・production確認はPhase 6で行う。

Phase 4では、その必要性と計画のみを確定する。

#### 10.4.12 失敗・中断時の対応を整理する

Phase 5で問題が発生した場合の基本対応を事前に決める。

##### テスト・validation失敗

- 原因を確認する
- Errorを残したまま次へ進まない
- 問題の原因となるPhaseへ必要に応じて戻る

##### 生成成果物の不一致

生成成果物を直接修正せず、原則として生成元・生成処理を確認する。

##### 想定外のGit差分

- 作業を停止する
- 差分の由来を確認する
- 勝手に削除・reset・stashしない

##### 設計上の問題発見

Phase 3へ戻る。

##### 要件・Scopeの問題発見

Phase 1へ戻る。

##### 現行仕様・影響範囲の不足発見

Phase 2へ戻る。

##### 作業前提・リポジトリ状態の問題

Phase 0へ戻る。

Phase 5で無理に設計変更を吸収しない。

#### 10.4.13 Phase 5開始前チェックリストを作成する

Phase 4終了時に、Phase 5へ進む前のチェックリストを整理する。

最低限、以下を確認する。

- 採用する設計が確定している
- 実装対象が明確
- 変更しない対象が明確
- 実装順序が明確
- 必要なテストが明確
- 必要な自動validationが明確
- 必要な手動確認が明確
- セキュリティ確認方法が明確
- Must要件と検証方法が対応している
- 文書更新対象が明確
- 生成・migration・公開影響が明確
- 失敗時の戻り先が明確
- `npm run validate:data` の実行が計画されている
- `npm run check` の実行が計画されている
- 未解決事項が明示されている
- 実装開始について利用者の明示承認を得る準備ができている

### 10.5 成果物

Phase 4終了時には、最低限以下が整理されている状態とする。

- 実装対象
- 変更しない対象
- 具体的な変更対象ファイル・ディレクトリ（確認できる範囲）
- 実装順序

- 新規テスト計画

- セキュリティ確認計画
- 要件・成功条件と検証方法の対応
- 文書更新計画
- 生成計画
- migration計画
- production公開影響
- 失敗・中断時の対応
- Phase 5開始前チェックリスト
- 未解決事項
- Phase 4終了判定

専用Markdownファイルを毎案件で新規作成することは必須としない。

### 10.6 完了条件

以下を満たした場合にPhase 4を完了できる。

- Phase 3の採用する設計に基づいて計画している
- 実装対象・変更しない対象を明確にしている
- 実装順序と依存関係を整理している
- 必要に応じて実装・PR単位を整理している
- 既存テストで確認できる範囲を把握している
- 必要な新規テストを計画している
- 自動validation計画を確定している
- `npm run validate:data` を必須として計画している
- `npm run check` を必須として計画している
- 必要な手動確認計画を確定している
- 必要なセキュリティ確認計画を確定している
- Must要件・安全性要件と検証方法を対応付けている
- 文書更新対象を整理している
- 生成・migration・公開影響を整理している
- 失敗・中断時の対応を整理している
- 未解決事項を明示している
- Phase 5へ安全に進めるか判断できる

### 10.7 終了判定

#### `PASS`

実装対象、順序、テスト、validation、手動確認、セキュリティ確認、文書更新、公開影響が必要な範囲で確定し、未解決事項なくPhase 5へ進める状態。

#### `PASS WITH OPEN ITEMS`

未解決事項はあるが、以下を満たす場合。

- 実装計画が確定している
- Must要件・安全性要件の検証方法が確定している
- Phase 5を安全に開始できる
- 未解決事項が実装開始を妨げない
- 解消する時期・Phaseが明確

未解決事項をPhase 5へ引き継ぐ。

#### `STOP`

例えば、

- 実装対象が不明
- 変更順序を安全に決められない
- Must要件の検証方法がない
- 必要なテスト方法を決められない
- セキュリティ確認方法が不足
- 生成元・生成先の関係が不明
- migration方法を決められない
- Phase 3の設計を実装計画へ落とせない

場合。

問題の発生元に応じてPhase 0〜3へ戻る。

#### `ON HOLD`

必要な計画検討を行っても、Phase 5を安全に開始できる計画を確定できない状態。

最低限以下を記録する。

- 保留理由
- 未確定の計画事項
- Phase 5へ進めない理由
- 再開条件

### 10.8 Phase 4で行わないこと

Phase 4では以下を行わない。

- コード変更
- データ変更
- Schema変更
- fixture変更
- HTML / CSS / JavaScript変更
- 画像変更
- 文書変更
- テストコード変更
- 生成成果物変更
- branch作成・切替
- commit
- push
- PR作成
- PRマージ
- production変更
- デプロイ
- migration実行
- テスト実行を伴う実装作業

Phase 4はあくまで、

> **採用する設計を、実装・検証可能な具体的計画へ落とし込むPhase**

とする。
