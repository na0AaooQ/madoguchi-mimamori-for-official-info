# 開発工程

## 文書の位置付け

この文書は、第一版を安全に実装・確認・公開するための工程1から工程13までを定めます。小さな縦切り実装、ローカル画面確認、修正、回帰テスト、検証環境、本番公開の順で段階的に進めます。

後続工程の詳細な製品・ライブラリ・ホスティング構成は、必要な判断材料が揃った段階で決定します。

## 全工程の原則

- 各工程の完了条件を満たしてから次へ進む
- 実装と同時に、該当する文書・検証・テストを更新する
- 自動検証と人による画面・内容確認を組み合わせる
- 現在状況の転載、内部情報の公開、日英の不整合を防ぐ
- 問題を修正した後は、同じ条件で再確認する
- 実際に見つかった不具合を再発防止の検証へ還元する

第一版のデータ設計、日英対応、検証・公開生成、段階的開発の判断を、既存文書とADRへ正式に反映します。

### 成果物

- 既存のREADME・設計・掲載・運用・サイト構成文書の更新
- データモデル文書
- 日英対応方針
- データ検証・公開生成方針
- 本開発工程文書
- 関連ADR

### 完了条件

- 多言語・データ形式・データ構造・検証が未確定という旧記載が解消されている
- 文書間の用語、状態値、ファイル名、相対リンクが整合している
- 実装コード、実データ、スキーマ、テスト、インフラを変更していない
- 文書検証が完了し、ドキュメント専用PRでレビューできる

## 工程2: 品質管理の土台

### 目的

データ・コード・文書の誤りを早期に検出するための最小の品質基盤を用意します。

### 成果物

- テストランナー
- Node.js 24.18.0・npm 11.16.0の固定設定
- ESLintによるJavaScript・JSON・GFM Markdown検査
- Prettierと既存Markdownの段階的ベースライン
- `node:test`による単体・CLIテスト
- AjvによるDraft 2020-12のテスト用Schema検証
- 日英locale、改訂番号、ID参照の最小意味検証
- fixture期待値検証
- 相対リンク、ADR、見出しの文書固有検証
- 品質管理手順とADR 0017

本番用`data/`、本番用`schemas/`、全意味検証、公開生成、画面は工程3以降の成果物であり、この工程では実装しません。

### 完了条件

- `npm ci`で依存関係を再現できる
- `npm run check`がファイルを書き換えずに全検証を実行できる
- 正常、検証Error、実行異常を終了コード`0`、`1`、`2`で区別できる
- 正常・異常fixtureの期待結果を確認できる
- JavaScript、JSON、Markdown、コードブロック、文書固有規則を検証できる
- 選定した製品、固定バージョン、運用手順、未実装範囲が文書化されている

## 工程3: データ基盤の実装

### 工程3-1: 共通Schema・空データ基盤（完了）

確定した管理単位に対し、core 14、日本語13、英語13の40データファイルと、core 14・locale 13の27 Schemaを配置しました。3つの`site.json`だけを単一オブジェクトとし、その他37ファイルは空の`items`を持つ配列エンベロープです。

日本語と英語は同じlocale Schemaを利用します。未実装の25 Schemaは`maxItems: 0`で保護し、ファイル配置、JSON構文、Schema、`$id`、siteの最小整合性を`npm run validate:data`で検証します。実在情報、正式なitem Schema、公開対象抽出、公開生成、画面は含みません。

### 工程3-2: 架空データの最小縦切り（次工程）

予約用途ドメインと明確な架空名称だけを使用し、データ読込と参照関係を最小の一経路で通します。対象となる管理単位だけに正式なitem Schemaと必要最小限の意味検証を追加し、工程3-1の空データ保護を段階的に解除します。

### 工程3の後続範囲

ID・URL重複、公式性根拠、表示期間、公開可能件数、内部項目除外などの全意味検証、公開対象抽出、公開成果物生成は、最小縦切りの検証後に段階実装します。実在する団体、URL、災害情報は、公式性と更新手順を確認するさらに後の工程で追加します。

## 工程4: 最小の縦切り画面

### 目的

データの読込から日英画面・外部案内までを、最小の一経路で通して検証します。

### 成果物

例として、次の縦切りを実装します。

日本語・英語トップ → 命・安全・医療 → 医療・救急相談カード → #7119などの公式案内先 → 確認日とリンク先言語の表示

実際の掲載内容は、実装時に公式情報を再確認して決定します。この例を実在URLや現在状況の確認なしに実データ化しません。

### 完了条件

- 日本語・英語の両方で一つの利用目的から公式案内先へ進める
- 公式名称、リンク先言語、確認日の表示方針を確認できる
- JavaScriptなしでも主要リンクと説明を利用できる
- 内部専用項目がブラウザへ送られていない

## 工程5: 第一版の画面と内容を段階追加

### 目的

最小縦切りで確認した方式を、第一版の必要範囲へ段階的に拡張します。

### 成果物

- 5分野
- 通常カード
- 公式団体・公式アカウント一覧
- 災害別案内
- このサイトについて・掲載方針
- 確認・更新履歴
- お問い合わせ・修正情報への導線

### 完了条件

- 第一版の5ページと主要導線が揃っている
- 各公開レコードに必要な日英localeと確認根拠がある
- 災害・出来事・3種類の関連データの責務が画面でも保たれている
- 現在状況、個人情報、推奨順位を表示していない

## 工程6: ローカル画面確認

### 目的

自動検証だけでは分からない表示、操作、表現、安全性の問題を、実際の画面で確認します。

### 対象画面幅

- 390px
- 480px
- 768px
- PC

### 確認内容

- 日本語・英語
- キーボード操作
- JavaScript無効時
- 意図しない横スクロール
- タップ領域
- 外部リンク
- リンク先言語表示
- 内部情報の非表示
- 保証表現の有無
- 現在状況の転載がないこと
- 見出し階層、フォーカス、ライト・ダーク双方の可読性

### 成果物

- 確認環境と条件の記録
- 画面ごとの確認結果
- 再現手順付きの問題一覧

### 完了条件

- 全対象幅と言語で確認結果が記録されている
- キーボードとJavaScript無効時の主要導線を確認している
- 見つかった問題が修正工程へ引き渡されている

## 工程7: 画面確認で見つかった問題の修正

### 目的

工程6で確認した表示、操作、内容、安全性の問題を解消します。

### 成果物

- 問題ごとの修正
- 影響する文書・データ・テストの更新
- 修正理由と影響範囲の記録

### 完了条件

- 各問題の対応状況を追跡できる
- 依頼範囲外の仕様変更を混在させていない
- 修正後の再確認条件が明確になっている

## 工程8: 同一条件での再確認

### 目的

修正が問題を解消し、別の画面・言語・操作条件へ回帰を生じさせていないことを確認します。

### 成果物

- 工程6と同じ画面幅・言語・操作条件の再確認結果
- 修正前後の比較記録
- 残課題の一覧

### 完了条件

- 工程6で見つかった問題を同じ手順で再現できない
- 日本語・英語、JavaScript無効時、キーボード操作に回帰がない
- 未解決事項を公開前レビューへ持ち越す場合、理由と影響が明記されている

## 工程9: 不具合を再発防止へ還元

### 目的

実際に見つかった不具合を、将来同じ段階で自動または手順的に検出できるようにします。

### 成果物

- 回帰テスト
- JSON Schema規則の追加・修正
- 意味検証規則の追加・修正
- Linter・Formatter設定の適切な更新
- 手動確認チェックリストの更新

### 完了条件

- 各重要不具合に、再発防止策または手動確認を選んだ理由がある
- 追加した検証が不具合を再現するケースで失敗し、修正後に成功する
- 過剰な誤検出や公開条件の緩和を招いていない

## 工程10: ローカル成果物の公開前レビュー

### 目的

検証環境へ出す前に、生成済みの公開成果物だけを対象として総合レビューします。

### 成果物

- 機械検証結果
- 人による日英・公式性・安全性・アクセシビリティ確認結果
- 公開ファイル一覧
- 内部項目非混入の確認結果
- 公開可否と残課題の記録

### 完了条件

- Errorがない
- Warningを人が確認している
- 意図した公式ページ、日英表現、リンク先言語を確認している
- 現在状況、個人情報、内部情報、保証表現を含んでいない
- ローカル成果物を検証環境へ出せると判断した根拠が記録されている

## 工程11: ホスティングとセキュリティ構成の検討

### 目的

確定した公開成果物と運用要件を基に、可用性、安全性、費用、保守性のバランスを検討します。

### 検討候補

- S3
- CDN
- 独自ドメイン
- SSL証明書
- DNS
- セキュリティヘッダー
- WAF
- ログ
- アクセス解析
- Cookie
- キャッシュ
- 404
- ロールバック
- 費用
- 障害時運用

この時点でもWAFを必須とは決めません。CloudFrontを含む具体的サービス、アクセスログ、アクセス解析、Cookie、CI/CD、自動デプロイも、要件とリスクを確認して個別に判断します。

### 成果物

- 候補比較
- 採否と理由を記録した設計文書・ADR
- セキュリティとプライバシーへの影響整理
- 検証環境・本番環境・ロールバックの運用案

### 完了条件

- 本番URL、ドメイン、SSL、DNS、キャッシュ、404、ログの責任範囲が明確である
- 公開対象ファイルと管理用ファイルの分離方法が明確である
- 障害時とロールバックの手順を検証できる
- 費用と継続運用を含めた採用理由が記録されている

## 工程12: 検証環境へのデプロイ

### 目的

実際の配信環境で、ローカルでは確認できないHTTPS、キャッシュ、公開範囲などを確認します。

### 成果物

- 検証環境への手順付きデプロイ
- HTTPS、日英表示、404、キャッシュの確認結果
- 外部リンクとリンク先言語の確認結果
- 公開ファイル一覧
- セキュリティヘッダーと内部ファイル非公開の確認結果

### 完了条件

- HTTPSで意図したコンテンツを表示できる
- 日本語・英語、404、キャッシュ更新を確認できる
- `data/core/`、内部確認履歴、非公開URL、ソースマップなど意図しないファイルが公開されていない
- 検証環境で見つかった問題が解消または明示的に判断されている

## 工程13: 本番デプロイと公開後確認

### 目的

承認済み成果物を本番へ公開し、公開直後の重大な配信・内容・リンク問題を検出します。

### 成果物

- 本番デプロイ記録
- 公開したコミットまたは成果物の識別情報
- 公開後のHTTPS、日英表示、404、主要導線、外部リンク確認
- 公開ファイル一覧と内部項目非混入の確認
- 必要に応じたロールバック記録

### 完了条件

- 承認済みの成果物と本番表示が一致する
- 主要な日英導線と公式案内先を確認している
- 内部情報、現在状況、個人情報が公開されていない
- 問題発生時にロールバックできる
- 公開後確認の結果と次回確認日が記録されている
